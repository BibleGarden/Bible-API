# Scripture Selection Benchmark

Эталонный набор для оценки качества серверного RAG-подбора мест Писания под
контекст молитвы (тема + разрешённые ответы пользователя из диалога Twinkler).
Тикет: ClickUp 86cb8vvyb. Статус: **approved** (версия 0.7.0) —
богословская/редакторская проверка завершена 2026-08-24, все 24 сценария
`review_status: approved`, набор утверждён Марией. Версия 0.3.0 добавляет
пакет ручных оценок Марии для 10 неразмеченных top-1 стадии финального
выбора (86cb8vw1h): 6 relevant, 3 acceptable и 1 unacceptable — Мф 10:28-31
для en-005 («не бойтесь убивающих тело»: опасное начало отрывка при
суицидально-чувствительном состоянии). Версия 0.4.0 добавляет второй пакет
оценок того же этапа — 4 новые грады (2 relevant, 2 acceptable). Версия
0.5.0 добавляет третий пакет — единственную оставшуюся неразмеченную
top-1 (uk-005, Іс 43:1-13 → `relevant`), см. «Редакторские решения по

top-1 прогона `npu` (ADR 0007): uk-005 → Ин 14:15-31 `relevant` (обещание
Утешителя «не полишу вас сиротами»), uk-007 → Пс 128:1-6 `relevant` (псалом

pytest-тест схемы лежит в `tests/` и попадает в общий прогон.

## Система координат (важно)

Ссылки на Писание — только числовые координаты
`book_number / chapter / verse_start / verse_end`.

- `book_number` — `cep_public.bible_books.number`, славянский порядок канона
  1–66: Быт=1, Пс=19, Мф=40, **Иак=45, 1Пет=46 … Рим=52** (соборные послания
  раньше павловых), Откр=66.
- **Псалтирь неоднородна по переводам.** Канон набора —
  `english-masoretic`: масоретские номера псалмов, надписания не нумеруются
  (как в `bsb`/`webus`/`webbe`). Фактическая нумерация в БД:
  - `syn`, `bti`, `npu` — септуагинтская нумерация глав, надписания посчитаны
    как стихи;
  - `ubh` — масоретские главы, но надписание = стих 1 (еврейская нумерация);
  - `bsb`, `webus`, `webbe` — канон набора, без сдвигов.

  Следствие: при резолве координат Псалтири для не-английских переводов
  **обязателен слой маппинга** (глава и стих). Это зафиксировано в
  `coordinate_system.psalm_mapping_required` (вопрос №1 в «Решённых вопросах»).
  Маппинг реализован проектно: `app/versification.py` + таблица
  `cep_public.psalm_verse_mappings` (ADR 0003); бенчмарк использует именно
  его (`retrieval_benchmark.load_psalm_maps`).
- **Покрытие переводов**: `npu` содержит только 28 книг (часть ВЗ + НЗ);
  полные Библии — `syn`, `bti`, `bsb`, `webus`, `webbe`, `ubh`. Проверка
  существования координат для украинского языка идёт по `ubh`.

## Формат сценария

```json
{
  "id": "ru-001",                  // ^(ru|en|uk)-\d{3}$, префикс = language
  "language": "ru",
  "category": "regular",           // regular|ambiguous|short|empty|sensitive
  "review_status": "draft",        // draft | approved (ставит рецензент)
  "prayer_context": {
    "topic": "…",                  // тема молитвы; "" только для category=empty
    "user_replies": ["…"]          // разрешённые ответы пользователя Twinkler
  },
  "notes": "заметка для рецензента (по-русски)",
  "references": [
    {"book_number": 19, "chapter": 127, "verse_start": 3, "verse_end": 5,
     "grade": "relevant", "reason": "почему такая оценка"}
  ]
}
```

Каждый сценарий содержит минимум 3 ссылки, среди них обязательно есть
`relevant` и `unacceptable`. Категории:

- `regular` — обычные темы (благодарность, работа, семья, прощение);
- `ambiguous` — неоднозначные темы («свет», «мир», «дорога», «отец»);
- `short` — сверхкороткие запросы (1–2 слова);
- `empty` — тема отсутствует (пустая строка, пустые ответы);
- `sensitive` — чувствительные состояния (горе, болезнь, тревога/паника,
  война, одиночество, ощущение никчёмности).

Важно: набор ссылок **не исчерпывающий** — в корпусе есть другие столь же
уместные отрывки, не попавшие в разметку. Поэтому метрики трактуются как
нижняя граница, а неразмеченный top-1 отправляется на ручную оценку
(`ungraded_review_required`).

## Критерии качества

Шкала ручной оценки совпадает со шкалой град в данных — 3 грады, без
промежуточных баллов (решение Марии, 2026-08-24):

| Града | Описание |
|-------|----------|
| relevant | Прямо отвечает теме и состоянию, целостен, бережен по тону |
| acceptable | Не противоречит теме, поддерживает молитву, но более общий/смещённый |
| unacceptable | Искажает смысл, звучит как обвинение/угроза/проклятие, лексическая ловушка, нет молитвенной ценности |

Пограничный случай («формально по теме, но натянуто») решается рецензентом
в пользу `acceptable` или `unacceptable`; в состоянии сомнения — понижать.
К каждой ручной оценке обязательно прилагается свободное текстовое поле
«почему» — краткое обоснование грады; оно используется для отладки промптов
и анализа промахов (в эталоне соответствует полю `reason`).

Аспекты, которые обязан проверить оценщик:

1. **Уместность** — отвечает ли отрывок теме и эмоциональному состоянию
   (не только ключевым словам). Лексическое совпадение при противоположном
   смысле («мир»/«не любите мира», «peace»/«not peace, but a sword») = 0.
2. **Контекстная целостность** — не вырван ли фрагмент из контекста так, что
   смысл искажается: слова друзей Иова, проклятия завета, нарративные
   эпизоды, гиперболы («возненавидь отца»), обещания конкретным адресатам.
3. **Тон и чувствительность** — в состояниях горя/болезни/кризиса недопустимы
   отрывки, читающиеся как обвинение, объяснение причины страдания или
   усиливающие отчаяние. Для category=sensitive любые сомнения = понижение.
4. **Целостность отрывка** — диапазон стихов образует законченную мысль
   (не обрывается посреди предложения, не начинается с «поэтому» без опоры).
5. **Разнообразие и повторы** (свойство системы, не отрывка) — в окне из N
   последовательных выборов не повторяется один и тот же отрывок и не
   доминирует одна книга; пороги — в `thresholds.json` (`diversity`).

## Метрики

Совпадение кандидата с эталонной ссылкой: равенство `book_number` и
`chapter` + пересечение диапазонов стихов (см. `matching_rule` в
`thresholds.json`).

Retrieval (top-K кандидатов до финального ранжирования):

- **hit_rate@K** — доля сценариев, где в top-K есть хотя бы одна `relevant`
  ссылка;
- **recall@K** — средняя по сценариям доля размеченных `relevant`, попавших в
  top-K (макро-усреднение);
- **MRR** — средний обратный ранг первой `relevant` ссылки;
- **unacceptable_share@K** — средняя доля `unacceptable` среди top-K.

Финальный выбор (top-1, то, что увидит пользователь):

- **relevant_share** — доля сценариев с top-1 = `relevant`;
- **relevant_or_acceptable_share** — доля сценариев с top-1 `relevant` или
  `acceptable`;
- **unacceptable_share** — доля сценариев с top-1 = `unacceptable`;
  требование тикета: **строго 0**, отдельно контролируется на
  category=sensitive;
- **sensitive_relevant_share** — доля sensitive-сценариев с top-1 =
  `relevant`; требование (ужесточение, согласовано 2026-08-24): **строго
  1.0** — для category=sensitive top-1 обязан иметь граду `relevant`,
  `acceptable` недостаточно (`sensitive_relevant_share_min` в
  `thresholds.json`);
- top-1, не попавший в разметку, оценивается вручную по 3-градовой шкале
  выше (с обязательным «почему») и без конвертации вливается в набор как
  новая града (пополнение разметки — часть процедуры прогона).

Разнообразие: прогон одного сценария N раз (или N дней подряд) — метрики
повторов и распределения по книгам в окне `no_repeat_window_selections`.

## Пороги

Значения — в `thresholds.json` (отдельный файл, чтобы согласование
порогов не смешивалось с правками разметки). Логика выбора: сначала жёсткая
безопасность (ноль явно неуместных в top-1; для sensitive top-1 строго
`relevant`), затем полезность (`relevant_or_acceptable >= 0.95`,
`relevant >= 0.70`), затем качество retrieval, достаточное для работы
ранжирования (`hit_rate@10 >= 0.90`, `MRR >= 0.60`).

**Статус: approved (версия 0.3.0)** — пороги согласованы Марией
2026-08-24: черновые значения приняты как есть, добавлено одно ужесточение —
`sensitive_relevant_share_min = 1.0` (для sensitive-сценариев top-1 обязан
быть `relevant`).

Версия 0.3.0 (2026-08-28, ADR 0007, решение делегировано оркестратору)
добавляет второй, необязательный раздел — `final_top1_coverage_restricted`.
Он применяется только к прогонам с намеренно суженным пулом кандидатов
(неполное покрытие перевода — `bti`, `webus`, `webbe`, `npu`, см.
«Симуляция суженного пула перевода» ниже) и держит ту же нулевую терпимость
к unacceptable и ту же строгую `sensitive_relevant_or_acceptable_share_min =
1.0`, что и основной раздел, но смягчает `sensitive_relevant_share_min` до
0.8 — в суженном пуле объективно меньше кандидатов из Ветхого Завета вне
Псалтири, и полный `1.0` по sensitive-relevant для такого пула недостижим
структурно, а не из-за качества ранжирования. Основной раздел `final_top1`
этим не затронут и продолжает применяться к полнокорпусным прогонам как
раньше.

## Процедура ручной оценки

1. Рецензент читает сценарий (тему и ответы) на языке сценария.
2. Для каждой ссылки открывает отрывок в переводе соответствующего языка
   (для Псалтири — с учётом маппинга нумерации) и проставляет граду по
   3-градовой шкале (`relevant` / `acceptable` / `unacceptable` — та же,
   что в данных, без промежуточных баллов) **и обязательно заполняет
   свободное текстовое поле «почему»** — краткое обоснование грады
   (служит для отладки промптов и анализа промахов).
3. Расхождение с текущей градой — правка грады + `reason`; спорные случаи
   помечаются в `notes` и решаются Марией. Ручные оценки вливаются в
   эталон без конвертации — как новые грады.
4. После проверки сценария: `review_status: approved`.
5. Когда все сценарии approved: `status: approved`, `approved_by`, bump
   минорной версии.

## Версионирование

- patch (0.1.x) — опечатки, уточнение reason/notes без смены град;
- minor (0.x.0) — изменение град, добавление/удаление сценариев или ссылок;
- major — изменение схемы или системы координат.

Правки согласуются через ревью; файл живёт в git вместе с кодом.

   ограничивается; `npu` (неполный, 28 книг) остаётся выбираемым вручную.
   Индексации подлежат **все семь переводов БД** (`syn`, `bti`, `ubh`,
   `npu`, `bsb`, `webus`, `webbe`); оставшиеся четыре (`bti`, `webus`,
   `webbe`, `npu`) доиндексируются после подтверждения качества бенчмарком
   на канонической тройке. Бенчмарк гоняется на канонических переводах.

## Прогон retrieval-пайплайна (ClickUp 86cb8vw1g)

Полный retrieval-слой (LLM-переформулировка -> гибридный поиск
embedding+BM25 -> interleave-слияние -> чёрный список жанров -> разнообразие
-> безопасный пул для пустой темы) прогоняется командой:

```bash
# venv бенчмарка (numpy+httpx+requests), Gemini-вызовы кэшируются на диск
python retrieval_benchmark.py pipeline            # утверждённая конфигурация
python retrieval_benchmark.py pipeline -h         # абляции: --no-rewrite,
                                                  # --no-lexical, --fusion, ...
```

> **Внимание, деньги.** Стадия rewrite использует `RETRIEVAL_REWRITE_API_KEY`,
> если он задан в окружении или в `Bible-API/.env` (внутрь контейнера его
> прокидывает compose), и `GEMINI_API_KEY` — если нет. Ключ rewrite платный:
> прогон `pipeline` без `--no-rewrite` тратит деньги на каждый непопавший в
> кэш сценарий. Чтобы принудительно считать по общему ключу, запускайте с
> `RETRIEVAL_REWRITE_API_KEY= python retrieval_benchmark.py pipeline`
> (пустое значение = «не задан») — но этот рецепт надёжен только внутри
> контейнера, где `.env` отсутствует: на машине с локальным `Bible-API/.env`

## Финальный выбор (ClickUp 86cb8vw1h)

Стадия обоснованного AI-выбора top-1 из кандидатов (grounded rerank,
`app/passage_rerank.py`) прогоняется поверх пайплайна:

```bash
python retrieval_benchmark.py pipeline --rerank   # модель из RETRIEVAL_RERANK_MODEL
python retrieval_benchmark.py pipeline --rerank --rerank-model gemini-3.5-flash-lite
```

Отчёт сверяет три политики top-1 с порогами `final_top1` из
`thresholds.json`: выбор reranker'а, fallback «ранг-1 retrieval» (что увидит
пользователь при отказе AI) и fallback «максимальный fused score».
Неразмеченные top-1 (не совпали ни с одной эталонной ссылкой) не считаются
ни успехом, ни провалом — печатаются отдельным списком для ручной оценки.
Ответы reranker'а кэшируются в `pipeline_cache.json` (ключ: модель, версия
промпта `RERANK_PROMPT_VERSION`, сценарий, hash списка кандидатов). Детали:
`../architect/adr/0005-grounded-passage-rerank.md`.

Результат на наборе 0.5.0 (прод-конфигурация gemini-3.5-flash-lite, промпт
v6, без изменений промпта — только новая града uk-005): relevant 0.917,

## Симуляция суженного пула перевода (ADR 0007)

С ADR 0007 отрывок может отдаваться в переводе, у которого нет собственного
чанк-корпуса (`bti`, `webus`, `webbe`, `npu`). Кандидаты при этом
фильтруются по «покрытию» — множеству канонических окон, все стихи которых
реально есть в этом переводе. Как это влияет на качество, проверяется тем же
пайплайном:

```bash
python retrieval_benchmark.py pipeline --rerank --coverage-translation 21
```

Флаг сужает кандидатов **только того языка**, которому принадлежит перевод
(остальные языки идут из кэша без единого нового вызова), покрытие строится
из `cep_public` (`app/passage_render.py`), корпус и промпт reranker'а не
меняются.

Прогон для `npu` (uk, 1167 из 3965 окон — только Псалтирь и Новый Завет) от
2026-08-27, 6 новых rerank-вызовов, результат —
`bench_data/results_adr0007_npu_coverage.json`. Он сделан до фильтра «окно =
собственный диапазон хранимого чанка опорного перевода» (ADR 0007, правка
F2), который сейчас применяет и сам флаг: с ним у `npu` 1163 окна, но ни
одно из четырёх выпавших окон не встречается в top-10 ни одного uk-сценария
этого прогона, поэтому цифры ниже остаются в силе.

Прогон также сделан до роста безопасного пула по OQ1: тогда
`data/safe_pool.json` содержал 6 мест, сейчас — 9. Это тоже не сдвигает
цифры: ни одно из трёх добавленных мест (Пс 121:1-8, Флп 4:1-9, Мф 6:25-34)
не совпадает с эталонными ссылками пустых сценариев (ru-009, en-006,
uk-006), а `rotate_safe_pool` отдаёт индексы пула в файловом порядке, и
новые записи добавлены в конец — ранги прежних мест не меняются (факт
проверен верификацией ревью 2026-08-28).

При этом расширении рассматривался и был отклонён кандидат Рим 8:26-39:
строка «за нас умерщвляют нас всякий день; считают нас за овец, обречённых
на заклание» (Рим 8:36) без сопровождающего контекста звучит опасно в
остром кризисном состоянии — на пустой теме или как fallback при недоступном
AI у пользователя нет ни диалога, ни reranker'а, которые могли бы направить
чтение к утешительной кульминации отрывка (ст. 38-39). Применено правило «в
сомнении — понижай»: отрывок остаётся доступен контекстно-зависимому
подбору (`select_final`), но не входит в безопасный пул для слепого показа.
Решение обратимо (Мария, 2026-08-28, ADR 0007, открытый вопрос 1; см. также
`app/data/safe_pool.json`).

**Колонки не сопоставимы напрямую — по двум разным причинам.**

Retrieval-строки базы взяты из сохранённых прогонов
`results_v050_flashlite_p6/p9.json`, посчитанных по `scenarios.json` 0.5.0 —
до вливания четвёртого пакета градаций (в HEAD 0.6.0); прогона базы на
текущем эталоне нет. Масштаб этой разницы видно внутри самого npu-прогона:
записи `details` для ru и en в нём **побайтово идентичны** базовым (фильтр
трогает только uk), а метрики всё равно другие — en recall 0.752 → 0.776,
ru 0.872 → 0.877. Это смена эталона, а не фича; прежняя формулировка «ru,
en без изменений» утверждала обратное и была неверна.

Строки final top-1 у обеих колонок пересчитаны по текущему эталону (0.7.0)
и теперь по одному и тому же множеству: версия 0.7.0 разметила top-1
uk-005 (Ин 14:15-31 → `relevant`) и uk-007 (Пс 128:1-6 → `relevant`), см.
«пятый пакет» во введении — прежнее расхождение знаменателей (22 против 24)
снято, в обеих колонках размечены все 24 top-1.

Порог `thresholds.json` для намеренно суженного пула больше не «формально
не применяется» — версия 0.3.0 добавила отдельный раздел
`final_top1_coverage_restricted` (решение Марии, 2026-08-28, делегировано
оркестратору): нуль unacceptable и `sensitive_relevant_or_acceptable_share_min
= 1.0` остаются такими же строгими, как в основном разделе, а
`sensitive_relevant_share_min` смягчён до 0.8 — суженный пул объективно
снижает шанс relevant-топ-1 по чувствительным сценариям из-за меньшего
числа кандидатов из Ветхого Завета вне Псалтири. Пересчёт прогона `npu` по
этому разделу:

#### Как варианты внедрены: опция `--rewrites-file`

В `retrieval_benchmark.py` добавлена **опция `pipeline --rewrites-file
<json>`** (чистое расширение, ни одна существующая ветка не изменена) —
переиспользуемый вход для любой внешней модели rewrite. При ней стадия
rewrite работает целиком с диска: `GeminiQueryRewriter` **вообще не
создаётся** (в `cmd_pipeline` конструктор теперь под `else`-веткой), поэтому
вызвать rewrite-провайдера прогон не может даже случайно. Сценарий, у
которого в файле стоит `error` или пустой список вариантов, идёт по той же
ветке деградации, что и живой `QueryRewriteError` (счётчик
`rewrite_failures` + поиск по сырому запросу) — то есть ровно как в проде
при `rewrite_failed`. Кэш `rewrites` в `pipeline_cache.json` при этом не
трогается (варианты детерминированы файлом); кэши `query_embeddings`
(ключ — хэш текста) и `reranks` (ключ включает хэш списка кандидатов)
работают штатно, поэтому новые варианты дают новые эмбеддинги и новые
rerank-вызовы, а совпавшие списки кандидатов переиспользуются.

```bash
docker cp evaluation/. bible-api:/code/evaluation
docker exec -w /code/evaluation bible-api python3 retrieval_benchmark.py \
  pipeline --rerank --rewrites-file bench_data/qwen_rewrites_v070.json \
  --json-out bench_data/results_v070_rewrite_qwen30b.json
docker exec -w /code/evaluation bible-api python3 retrieval_benchmark.py \
  pipeline --rerank --coverage-translation 21 \
  --rewrites-file bench_data/qwen_rewrites_v070.json \
  --json-out bench_data/results_v070_rewrite_qwen30b_npu_coverage.json
```

Оба прогона выполнялись через обёртку, которая перед `main()` подменяет
`GeminiQueryRewriter.__init__`/`.rewrite` на выбрасывающую заглушку
(tripwire). Обе команды завершились с `TRIPWIRE OK`, число ключей в
`cache["rewrites"]` до и после пакета одинаково (274 → 274) — вызовов
rewrite-провайдера не было ни одного. Свежие вызовы пакета: **114

#### Как сгенерированы переформулировки

Одноразовым скриптом (в репозиторий не входит), импортирующим боевые
`build_rewrite_instruction` / `build_rewrite_user_content` /
`parse_rewrite_response` из `app/query_rewrite.py`, — то есть промпт
побайтово тот же, что у живой стадии rewrite. Вызовы — OpenAI-совместимый
`POST /api/v1/chat/completions` OpenRouter: system = инструкция,
user = пользовательский контент, `temperature=0.0`, `max_tokens=8192`,
`response_format={"type":"json_object"}` (перенос `maxOutputTokens` /
`temperature` / `responseMimeType` из `GeminiQueryRewriter.rewrite`).
Markdown-обёртку стрипает штатный `parse_rewrite_response`. Невалидный
JSON — один повтор, транспорт — до трёх попыток; замерялся wall-time
каждого сценария. Ключ читался из `.env` внутри процесса и попадал только
в заголовок `Authorization`.

Артефакты: `bench_data/glm53flash_rewrites_v070.json`,
`bench_data/deepseekv4flash_rewrites_v070.json` — формат
`qwen_rewrites_v070.json` (meta: точный OpenRouter ID, версия промпта,
версия эталона, параметры сэмплинга, стоимость; по сценарию — варианты,

#### Домер: GLM-5.3-Flash с reasoning effort=low (ClickUp 86cbbmpp7)

**Дата прогона: 2026-08-29.** Прямое продолжение рекомендации предыдущей
подсекции: GLM-5.3-Flash взял все четыре retrieval-порога основного
прогона, но с дефолтным рассуждением (effort `max`) медиана вызова 35 с при
бюджете запроса 15 с. Здесь тот же замер повторён с **единственным
отличием** — в запрос добавлен параметр OpenRouter `reasoning: {"effort":
"low"}`. Всё остальное байт-в-байт как в 86cbbmhk8: те же 24 сценария
эталона 0.7.0, тот же боевой промпт rewrite v7 из `app/query_rewrite.py`,
тот же сэмплинг (`temperature=0.0`, `max_tokens=8192`,
`response_format={"type":"json_object"}`), тот же JSON-контракт, те же
ретраи (невалидный JSON — один повтор, транспорт — до трёх попыток), тот же
rerank `gemini-3.5-flash-lite`, те же пороги 0.3.0.

`supported_parameters` содержит и `reasoning`, и `reasoning_effort`;
использован унифицированный объект `reasoning: {"effort": "low"}`.

**Параметр реально применяется — подтверждено контрольным A/B на одном
сценарии (ru-002, один и тот же провайдер Z.AI, одинаковые 554 prompt-токена):**

|---|---|---|---|---|
| без параметра (дефолт `max`) | 3102 | **2884** | 8994 знака | 48.4 с |

* **Обмен получился прямой: вся задержка ушла, вместе с ней ушло и
  качество.** Медиана 35.0 → 4.4 с (максимум 202.7 → 6.5 с) — по этому
  критерию конфигурация укладывается в 15-секундный бюджет с запасом и
  стабильнее базы. Но платой стали −0.133 recall и −0.090 MRR, а
  coverage-recall вместо промаха на 0.001 промахивается на 0.127
  (0.599 → 0.473).
* **Открытые вопросы предыдущего пакета `low` не закрывает.**
  Coverage-recall ушёл дальше от порога; гейт ручной разметки открыт шире
  (8 неразмеченных top-1 против 5 и 6), знаменатель `final_top1` упал до
  16/24, а чувствительных сценариев размечено 4 из 7 — так что высокая доля
  `relevant` 0.938 здесь менее доказательна, чем 0.842 у `max`.
* **Промежуточных режимов имеет смысл ждать немного.** У GLM `low`
  фактически означает «рассуждения нет» (0 reasoning-токенов на 18 из 24
  сценариев), то есть измерены не «low против max», а два края шкалы. Если
  Мария захочет ещё одну попытку по этому кандидату, содержательным будет
  `medium` (≈50% бюджета) — он единственный может дать компромисс между
  35 с/0.649 и 4.4 с/0.516. Из одних наших цифр рекомендовать его нельзя:
  неизвестно, где на шкале лежит порог 0.60 по recall и укладывается ли
  соответствующая задержка в 15 с.
* **Переключение не выполнено.** Конфигурация сервиса этим пакетом не
  менялась: `.env` не редактировался, `RETRIEVAL_REWRITE_MODEL` и
  `RETRIEVAL_RERANK_MODEL` оставлены как были; прод-адаптер под OpenRouter
  не писался (вне скоупа). Rewrite в обоих прогонах читался с диска
  (`--rewrites-file`), rerank в логах обоих прогонов —
  `gemini-3.5-flash-lite`, как и в пакете 86cbbmhk8.
