## Система координат (важно)

Ссылки на Писание — только числовые координаты
`book_number / chapter / verse_start / verse_end`.

- `book_number` — `cep_public.bible_books.number`, славянский порядок канона
  1–66: Быт=1, Пс=19, Мф=40, **Иак=45, 1Пет=46 … Рим=52** (соборные послания
  раньше павловых), Откр=66.
- **Псалтирь неоднородна по переводам.** Канон набора —
  `english-masoretic`: масоретские номера псалмов, надписания не нумеруются
  (как в `bsb`/`webus`/`webbe`). Фактическая нумерация в БД:
  - `syn`, `bti`, `npu` — септуагинтская нумерация глав, надписания посчитаны
    как стихи;
  - `ubh` — масоретские главы, но надписание = стих 1 (еврейская нумерация);
  - `bsb`, `webus`, `webbe` — канон набора, без сдвигов.

  Следствие: при резолве координат Псалтири для не-английских переводов
  **обязателен слой маппинга** (глава и стих). Это зафиксировано в
  `coordinate_system.psalm_mapping_required` (вопрос №1 в «Решённых вопросах»).
  Маппинг реализован проектно: `app/versification.py` + таблица
  `cep_public.psalm_verse_mappings` (ADR 0003); бенчмарк использует именно
  его (`retrieval_benchmark.load_psalm_maps`).
- **Покрытие переводов**: `npu` содержит только 28 книг (часть ВЗ + НЗ);
  полные Библии — `syn`, `bti`, `bsb`, `webus`, `webbe`, `ubh`. Проверка
  существования координат для украинского языка идёт по `ubh`.

## Формат сценария

```json
{
  "id": "ru-001",                  // ^(ru|en|uk)-\d{3}$, префикс = language
  "language": "ru",
  "category": "regular",           // regular|ambiguous|short|empty|sensitive
  "review_status": "draft",        // draft | approved (ставит рецензент)
  "prayer_context": {
    "topic": "…",                  // тема молитвы; "" только для category=empty
    "user_replies": ["…"]          // разрешённые ответы пользователя Twinkler
  },
  "notes": "заметка для рецензента (по-русски)",
  "references": [
    {"book_number": 19, "chapter": 127, "verse_start": 3, "verse_end": 5,
     "grade": "relevant", "reason": "почему такая оценка"}
  ]
}
```

Каждый сценарий содержит минимум 3 ссылки, среди них обязательно есть
`relevant` и `unacceptable`. Категории:

- `regular` — обычные темы (благодарность, работа, семья, прощение);
- `ambiguous` — неоднозначные темы («свет», «мир», «дорога», «отец»);
- `short` — сверхкороткие запросы (1–2 слова);
- `empty` — тема отсутствует (пустая строка, пустые ответы);
- `sensitive` — чувствительные состояния (горе, болезнь, тревога/паника,
  война, одиночество, ощущение никчёмности).

Важно: набор ссылок **не исчерпывающий** — в корпусе есть другие столь же
уместные отрывки, не попавшие в разметку. Поэтому метрики трактуются как
нижняя граница, а неразмеченный top-1 отправляется на ручную оценку
(`ungraded_review_required`).

## Критерии качества

Шкала ручной оценки совпадает со шкалой град в данных — 3 грады, без
промежуточных баллов (решение Марии, 2026-08-24):

| Града | Описание |
|-------|----------|
| relevant | Прямо отвечает теме и состоянию, целостен, бережен по тону |
| acceptable | Не противоречит теме, поддерживает молитву, но более общий/смещённый |
| unacceptable | Искажает смысл, звучит как обвинение/угроза/проклятие, лексическая ловушка, нет молитвенной ценности |

Пограничный случай («формально по теме, но натянуто») решается рецензентом
в пользу `acceptable` или `unacceptable`; в состоянии сомнения — понижать.
К каждой ручной оценке обязательно прилагается свободное текстовое поле
«почему» — краткое обоснование грады; оно используется для отладки промптов
и анализа промахов (в эталоне соответствует полю `reason`).

Аспекты, которые обязан проверить оценщик:

1. **Уместность** — отвечает ли отрывок теме и эмоциональному состоянию
   (не только ключевым словам). Лексическое совпадение при противоположном
   смысле («мир»/«не любите мира», «peace»/«not peace, but a sword») = 0.
2. **Контекстная целостность** — не вырван ли фрагмент из контекста так, что
   смысл искажается: слова друзей Иова, проклятия завета, нарративные
   эпизоды, гиперболы («возненавидь отца»), обещания конкретным адресатам.
3. **Тон и чувствительность** — в состояниях горя/болезни/кризиса недопустимы
   отрывки, читающиеся как обвинение, объяснение причины страдания или
   усиливающие отчаяние. Для category=sensitive любые сомнения = понижение.
4. **Целостность отрывка** — диапазон стихов образует законченную мысль
   (не обрывается посреди предложения, не начинается с «поэтому» без опоры).
5. **Разнообразие и повторы** (свойство системы, не отрывка) — в окне из N
   последовательных выборов не повторяется один и тот же отрывок и не
   доминирует одна книга; пороги — в `thresholds.json` (`diversity`).

## Метрики

Совпадение кандидата с эталонной ссылкой: равенство `book_number` и
`chapter` + пересечение диапазонов стихов (см. `matching_rule` в
`thresholds.json`).

Retrieval (top-K кандидатов до финального ранжирования):

- **hit_rate@K** — доля сценариев, где в top-K есть хотя бы одна `relevant`
  ссылка;
- **recall@K** — средняя по сценариям доля размеченных `relevant`, попавших в
  top-K (макро-усреднение);
- **MRR** — средний обратный ранг первой `relevant` ссылки;
- **unacceptable_share@K** — средняя доля `unacceptable` среди top-K.

Финальный выбор (top-1, то, что увидит пользователь):

- **relevant_share** — доля сценариев с top-1 = `relevant`;
- **relevant_or_acceptable_share** — доля сценариев с top-1 `relevant` или
  `acceptable`;
- **unacceptable_share** — доля сценариев с top-1 = `unacceptable`;
  требование тикета: **строго 0**, отдельно контролируется на
  category=sensitive;
- **sensitive_relevant_share** — доля sensitive-сценариев с top-1 =
  `relevant`; требование (ужесточение, согласовано 2026-08-24): **строго
  1.0** — для category=sensitive top-1 обязан иметь граду `relevant`,
  `acceptable` недостаточно (`sensitive_relevant_share_min` в
  `thresholds.json`);
- top-1, не попавший в разметку, оценивается вручную по 3-градовой шкале
  выше (с обязательным «почему») и без конвертации вливается в набор как
  новая града (пополнение разметки — часть процедуры прогона).

Разнообразие: прогон одного сценария N раз (или N дней подряд) — метрики
повторов и распределения по книгам в окне `no_repeat_window_selections`.

## Пороги

Значения — в `thresholds.json` (отдельный файл, чтобы согласование
порогов не смешивалось с правками разметки). Логика выбора: сначала жёсткая
безопасность (ноль явно неуместных в top-1; для sensitive top-1 строго
`relevant`), затем полезность (`relevant_or_acceptable >= 0.95`,
`relevant >= 0.70`), затем качество retrieval, достаточное для работы
ранжирования (`hit_rate@10 >= 0.90`, `MRR >= 0.60`).

**Статус: approved (версия 0.3.0)** — пороги согласованы Марией
2026-08-24: черновые значения приняты как есть, добавлено одно ужесточение —
`sensitive_relevant_share_min = 1.0` (для sensitive-сценариев top-1 обязан
быть `relevant`).

Версия 0.3.0 (2026-08-28, ADR 0007, решение делегировано оркестратору)
добавляет второй, необязательный раздел — `final_top1_coverage_restricted`.
Он применяется только к прогонам с намеренно суженным пулом кандидатов
(неполное покрытие перевода — `bti`, `webus`, `webbe`, `npu`, см.
«Симуляция суженного пула перевода» ниже) и держит ту же нулевую терпимость
к unacceptable и ту же строгую `sensitive_relevant_or_acceptable_share_min =
1.0`, что и основной раздел, но смягчает `sensitive_relevant_share_min` до
0.8 — в суженном пуле объективно меньше кандидатов из Ветхого Завета вне
Псалтири, и полный `1.0` по sensitive-relevant для такого пула недостижим
структурно, а не из-за качества ранжирования. Основной раздел `final_top1`
этим не затронут и продолжает применяться к полнокорпусным прогонам как
раньше.

## Процедура ручной оценки

1. Рецензент читает сценарий (тему и ответы) на языке сценария.
2. Для каждой ссылки открывает отрывок в переводе соответствующего языка
   (для Псалтири — с учётом маппинга нумерации) и проставляет граду по
   3-градовой шкале (`relevant` / `acceptable` / `unacceptable` — та же,
   что в данных, без промежуточных баллов) **и обязательно заполняет
   свободное текстовое поле «почему»** — краткое обоснование грады
   (служит для отладки промптов и анализа промахов).
3. Расхождение с текущей градой — правка грады + `reason`; спорные случаи
   помечаются в `notes` и решаются Марией. Ручные оценки вливаются в
   эталон без конвертации — как новые грады.
4. После проверки сценария: `review_status: approved`.
5. Когда все сценарии approved: `status: approved`, `approved_by`, bump
   минорной версии.

## Версионирование

- patch (0.1.x) — опечатки, уточнение reason/notes без смены град;
- minor (0.x.0) — изменение град, добавление/удаление сценариев или ссылок;
- major — изменение схемы или системы координат.

Правки согласуются через ревью; файл живёт в git вместе с кодом.

   ClickUp 86cb8vw1g), здесь фиксируется только политика.
7. ~~Языковая политика: канонические переводы~~ — **закрыто 2026-08-24,

## Прогон retrieval-пайплайна (ClickUp 86cb8vw1g)

Полный retrieval-слой (LLM-переформулировка -> гибридный поиск
embedding+BM25 -> interleave-слияние -> чёрный список жанров -> разнообразие
-> безопасный пул для пустой темы) прогоняется командой:

```bash
# venv бенчмарка (numpy+httpx+requests), Gemini-вызовы кэшируются на диск
python retrieval_benchmark.py pipeline            # утверждённая конфигурация
python retrieval_benchmark.py pipeline -h         # абляции: --no-rewrite,
                                                  # --no-lexical, --fusion, ...
```

> **Внимание, деньги.** Стадия rewrite использует `AI_SCRIPTURE_REWRITE_API_KEY`,
> если он задан в окружении или в `Bible-API/.env` (внутрь контейнера его
> прокидывает compose), и `GEMINI_API_KEY` — если нет. Ключ rewrite платный:
> прогон `pipeline` без `--no-rewrite` тратит деньги на каждый непопавший в
> кэш сценарий. Чтобы принудительно считать по общему ключу, запускайте с
> `AI_SCRIPTURE_REWRITE_API_KEY= python retrieval_benchmark.py pipeline`
> (пустое значение = «не задан») — но этот рецепт надёжен только внутри
> контейнера, где `.env` отсутствует: на машине с локальным `Bible-API/.env`
> пустая переменная проваливается в чтение файла и вернёт всё тот же платный
> ключ, поэтому там нужно временно закомментировать `AI_SCRIPTURE_REWRITE_API_KEY`
> в самом `.env`. Эмбеддинги и rerank по-прежнему идут по `GEMINI_API_KEY`.
>
> **`--embedder` от этого не спасает** (86cbe4n7e). Локальный эмбеддер
> заменяет только стадию эмбеддинга: `pipeline --embedder e5-small` без
> `--rewrites-file`/`--no-rewrite` всё так же дойдёт до стадии rewrite и
> потратит платный ключ. Прогон полностью бесплатен и не требует
> `GEMINI_API_KEY` только при сочетании «локальный `--embedder` +
> (`--rewrites-file` или `--no-rewrite`) + без `--rerank`».

Дефолтные флаги воспроизводят утверждённую конфигурацию (rewrite
gemini-3.7-flash, prompt v7, 6 вариантов, interleave, BM25 k=20, blacklist,
pool, cap 4/книга и 1/глава). Результат на approved-наборе v0.2.0: hit@10
0.958, recall@10 0.753, MRR 0.650, unacc@10 0.000 — все пороги
`retrieval_top_k` пройдены (детали и абляции:
`../architect/adr/0004-retrieval-pipeline.md`, свежий прогон —
`bench_data/results_pipeline_final.json`). Кэш Gemini-вызовов —
`bench_data/pipeline_cache.json`; смена промпта (`REWRITE_PROMPT_VERSION`)
или модели инвалидирует ключи кэша автоматически.

Статус решений 5 и 6: реализованы в `app/data/safe_pool.json` и
`app/data/genre_blacklist.json`; эталонные жанровые ловушки закреплены
регресс-тестами `tests/test_retrieval.py`.

## Финальный выбор (ClickUp 86cb8vw1h)

Стадия обоснованного AI-выбора top-1 из кандидатов (grounded rerank,
`app/passage_rerank.py`) прогоняется поверх пайплайна:

```bash
python retrieval_benchmark.py pipeline --rerank   # модель из AI_SCRIPTURE_RERANK_MODEL
python retrieval_benchmark.py pipeline --rerank --rerank-model gemini-3.5-flash-lite
```

Отчёт сверяет три политики top-1 с порогами `final_top1` из
`thresholds.json`: выбор reranker'а, fallback «ранг-1 retrieval» (что увидит
пользователь при отказе AI) и fallback «максимальный fused score».
Неразмеченные top-1 (не совпали ни с одной эталонной ссылкой) не считаются
ни успехом, ни провалом — печатаются отдельным списком для ручной оценки.
Ответы reranker'а кэшируются в `pipeline_cache.json` (ключ: модель, версия
промпта `RERANK_PROMPT_VERSION`, сценарий, hash списка кандидатов). Детали:
`../architect/adr/0005-grounded-passage-rerank.md`.

Результат на наборе 0.5.0 (прод-конфигурация gemini-3.5-flash-lite, промпт
v6, без изменений промпта — только новая града uk-005): relevant 0.917,
relevant-or-acceptable 1.000, unacceptable 0, sensitive relevant 1.000
(graded 24/24, sensitive 7/7) — все пороги `final_top1` пройдены; свежий
прогон — `bench_data/results_v050_flashlite_p6.json` (прогон из кэша,
`fresh_calls=0`; сравнения на прежнем наборе 0.4.0:
`results_v040_flashlite_p6.json` — та же конфигурация до градации uk-005,
`results_v040_flashlite_p4.json` — прежний промпт на том наборе,
`results_v040_flashlite_p5.json` — промежуточная версия правила,
`results_v040_flash_p{4,5,6}.json` — альтернативная модель
gemini-3.7-flash; на v6 она проваливает sensitive-порог, 0.800, поэтому

Ручные оценки Марии вливаются в эталон как новые грады (см. «Процедуру
ручной оценки»), а вытекающие из них правила — в промпт reranker'а
**обобщённо, без упоминания конкретных мест и сценариев**:

| Версия промпта | Правило (обобщённое) | Повод |
|---|---|---|
| v2 | в реальной опасности/болезни предпочитать присутствие и прибежище Божие, а не обещания, звучащие как гарантия физической безопасности | uk-002: Пс 91 понижен редактором до `acceptable` |
| v4 | для уязвимых состояний не выбирать отрывок, **первая фраза** которого несёт образы смерти/насилия/суда/геенны, даже если ядро утешительно (мягкая формулировка v3 моделью игнорировалась — переписано как явная проверка первой фразы) | en-005: Мф 10:28-31 оценён `unacceptable` |
| v5 | ту же проверку довести **до последней строки отрывка**: для уязвимых состояний не выбирать кандидата, который где-либо внутри подаёт беду как наказание, связывает страдание с грехом молящегося или переключается на врагов/предательство — при наличии кандидата, утешительного от первой строки до последней; ограничение сформулировано так, чтобы отключалась только эта дополнительная проверка, а не остальные правила безопасности | ru-004: Пс 41 оценён `acceptable` |

## Симуляция суженного пула перевода (ADR 0007)

С ADR 0007 отрывок может отдаваться в переводе, у которого нет собственного
чанк-корпуса (`bti`, `webus`, `webbe`, `npu`). Кандидаты при этом
фильтруются по «покрытию» — множеству канонических окон, все стихи которых
реально есть в этом переводе. Как это влияет на качество, проверяется тем же
пайплайном:

```bash
python retrieval_benchmark.py pipeline --rerank --coverage-translation 21
```

Флаг сужает кандидатов **только того языка**, которому принадлежит перевод
(остальные языки идут из кэша без единого нового вызова), покрытие строится
из `cep_public` (`app/passage_render.py`), корпус и промпт reranker'а не
меняются.

Прогон для `npu` (uk, 1167 из 3965 окон — только Псалтирь и Новый Завет) от
2026-08-27, 6 новых rerank-вызовов, результат —
`bench_data/results_adr0007_npu_coverage.json`. Он сделан до фильтра «окно =
собственный диапазон хранимого чанка опорного перевода» (ADR 0007, правка
F2), который сейчас применяет и сам флаг: с ним у `npu` 1163 окна, но ни
одно из четырёх выпавших окон не встречается в top-10 ни одного uk-сценария
этого прогона, поэтому цифры ниже остаются в силе.

Прогон также сделан до роста безопасного пула по OQ1: тогда
`data/safe_pool.json` содержал 6 мест, сейчас — 9. Это тоже не сдвигает
цифры: ни одно из трёх добавленных мест (Пс 121:1-8, Флп 4:1-9, Мф 6:25-34)
не совпадает с эталонными ссылками пустых сценариев (ru-009, en-006,
uk-006), а `rotate_safe_pool` отдаёт индексы пула в файловом порядке, и
новые записи добавлены в конец — ранги прежних мест не меняются (факт
проверен верификацией ревью 2026-08-28).

При этом расширении рассматривался и был отклонён кандидат Рим 8:26-39:
строка «за нас умерщвляют нас всякий день; считают нас за овец, обречённых
на заклание» (Рим 8:36) без сопровождающего контекста звучит опасно в
остром кризисном состоянии — на пустой теме или как fallback при недоступном
AI у пользователя нет ни диалога, ни reranker'а, которые могли бы направить
чтение к утешительной кульминации отрывка (ст. 38-39). Применено правило «в
сомнении — понижай»: отрывок остаётся доступен контекстно-зависимому
подбору (`select_final`), но не входит в безопасный пул для слепого показа.
Решение обратимо (Мария, 2026-08-28, ADR 0007, открытый вопрос 1; см. также
`app/data/safe_pool.json`).

| метрика | база (ubh) | npu |
|---|---|---|

#### Как варианты внедрены: опция `--rewrites-file`

В `retrieval_benchmark.py` добавлена **опция `pipeline --rewrites-file
<json>`** (чистое расширение, ни одна существующая ветка не изменена) —
переиспользуемый вход для любой внешней модели rewrite. При ней стадия
rewrite работает целиком с диска: `GeminiQueryRewriter` **вообще не
создаётся** (в `cmd_pipeline` конструктор теперь под `else`-веткой), поэтому
вызвать rewrite-провайдера прогон не может даже случайно. Сценарий, у
которого в файле стоит `error` или пустой список вариантов, идёт по той же
ветке деградации, что и живой `QueryRewriteError` (счётчик
`rewrite_failures` + поиск по сырому запросу) — то есть ровно как в проде
при `rewrite_failed`. Кэш `rewrites` в `pipeline_cache.json` при этом не
трогается (варианты детерминированы файлом); кэши `query_embeddings`
(ключ — хэш текста) и `reranks` (ключ включает хэш списка кандидатов)
работают штатно, поэтому новые варианты дают новые эмбеддинги и новые
rerank-вызовы, а совпавшие списки кандидатов переиспользуются.

```bash
docker cp evaluation/. bible-api:/code/evaluation
docker exec -w /code/evaluation bible-api python3 retrieval_benchmark.py \
  pipeline --rerank --rewrites-file bench_data/qwen_rewrites_v070.json \
  --json-out bench_data/results_v070_rewrite_qwen30b.json
docker exec -w /code/evaluation bible-api python3 retrieval_benchmark.py \
  pipeline --rerank --coverage-translation 21 \
  --rewrites-file bench_data/qwen_rewrites_v070.json \
  --json-out bench_data/results_v070_rewrite_qwen30b_npu_coverage.json
```

`GeminiQueryRewriter.__init__`/`.rewrite` на выбрасывающую заглушку
(tripwire). Обе команды завершились с `TRIPWIRE OK`, число ключей в
`cache["rewrites"]` до и после пакета одинаково (274 → 274) — вызовов
rewrite-провайдера не было ни одного. Свежие вызовы пакета: **114

#### Как сгенерированы переформулировки

Одноразовым скриптом (в репозиторий не входит), импортирующим боевые
`build_rewrite_instruction` / `build_rewrite_user_content` /
`parse_rewrite_response` из `app/query_rewrite.py`, — то есть промпт
побайтово тот же, что у живой стадии rewrite. Вызовы — OpenAI-совместимый
`POST /api/v1/chat/completions` OpenRouter: system = инструкция,
user = пользовательский контент, `temperature=0.0`, `max_tokens=8192`,
`response_format={"type":"json_object"}` (перенос `maxOutputTokens` /
`temperature` / `responseMimeType` из `GeminiQueryRewriter.rewrite`).
Markdown-обёртку стрипает штатный `parse_rewrite_response`. Невалидный
JSON — один повтор, транспорт — до трёх попыток; замерялся wall-time
каждого сценария. Ключ читался из `.env` внутри процесса и попадал только
в заголовок `Authorization`.

Артефакты: `bench_data/glm53flash_rewrites_v070.json`,
`bench_data/deepseekv4flash_rewrites_v070.json` — формат
`qwen_rewrites_v070.json` (meta: точный OpenRouter ID, версия промпта,
версия эталона, параметры сэмплинга, стоимость; по сценарию — варианты,
latency, attempts, error).

Сценарии категории `empty` (ru-009, en-006, uk-006) прогонялись через ту же
ветку, что и остальные, — как в qwen-артефакте. Обе модели по ним ответили
успешно, но на результат это не влияет: `empty` бенчмарк (и прод)
обрабатывает **до** стадии rewrite безопасным пулом.

**У обоих кандидатов 24 из 24 сценариев переформулированы успешно**, по 6
вариантов, `error` нет ни одного. Поэтому `rewrite_failures = 0` во всех

(у qwen для сравнения был один отказ, en-006).

#### Домер: GLM-5.3-Flash с reasoning effort=low (ClickUp 86cbbmpp7)

**Дата прогона: 2026-08-29.** Прямое продолжение рекомендации предыдущей
подсекции: GLM-5.3-Flash взял все четыре retrieval-порога основного
прогона, но с дефолтным рассуждением (effort `max`) медиана вызова 35 с при
бюджете запроса 15 с. Здесь тот же замер повторён с **единственным
отличием** — в запрос добавлен параметр OpenRouter `reasoning: {"effort":
"low"}`. Всё остальное байт-в-байт как в 86cbbmhk8: те же 24 сценария
эталона 0.7.0, тот же боевой промпт rewrite v7 из `app/query_rewrite.py`,
тот же сэмплинг (`temperature=0.0`, `max_tokens=8192`,
`response_format={"type":"json_object"}`), тот же JSON-контракт, те же
ретраи (невалидный JSON — один повтор, транспорт — до трёх попыток), тот же
rerank `gemini-3.5-flash-lite`, те же пороги 0.3.0.

Синтаксис проверен по каталогу и доке: у `z-ai/glm-5.3-flash`
`supported_parameters` содержит и `reasoning`, и `reasoning_effort`;
использован унифицированный объект `reasoning: {"effort": "low"}`.

**Параметр реально применяется — подтверждено контрольным A/B на одном
сценарии (ru-002, один и тот же провайдер Z.AI, одинаковые 554 prompt-токена):**

| | completion-токены | из них reasoning | поле `message.reasoning` | wall-time |
|---|---|---|---|---|
| без параметра (дефолт `max`) | 3102 | **2884** | 8994 знака | 48.4 с |
| `reasoning.effort=low` | 174 | **0** | пусто | 4.2 с |

То есть на `low` GLM-5.3-Flash не «думает меньше», а на этих запросах
перестаёт выдавать трассу рассуждения вовсе. По всему прогону из 24
сценариев reasoning-токены ненулевые лишь в шести (7-72 токена), медиана 0,
сумма 120 против ~1.9 тыс. **на вызов** у `max`.

(`meta.model = "z-ai/glm-5.3-flash (reasoning=low)"`, в `meta.sampling`
добавлен блок `reasoning`). **24 из 24 сценариев переформулированы
успешно**, по 6 вариантов, ни одной ошибки и ни одного повтора из-за
невалидного JSON (у `max` их было два). Маршрутизация провайдера, как и

##### Вердикт

* **`z-ai/glm-5.3-flash` с `reasoning.effort=low` — не проходит, и, в
  отличие от `max`, у этой конфигурации нет перспективы.** Задача домера
  ставила ключевой вопрос «держится ли качество retrieval при low» — ответ
  **нет**: recall@10 0.516 при пороге 0.60 (было 0.649 PASS) и MRR 0.571
  при 0.60 (было 0.661 PASS). Кандидат, единственный бравший все четыре
  порога основного прогона, теряет два из них.
* **Обмен получился прямой: вся задержка ушла, вместе с ней ушло и
  качество.** Медиана 35.0 → 4.4 с (максимум 202.7 → 6.5 с) — по этому
  критерию конфигурация укладывается в 15-секундный бюджет с запасом и
  стабильнее базы. Но платой стали −0.133 recall и −0.090 MRR, а
  coverage-recall вместо промаха на 0.001 промахивается на 0.127
  (0.599 → 0.473).
* **Открытые вопросы предыдущего пакета `low` не закрывает.**
  Coverage-recall ушёл дальше от порога; гейт ручной разметки открыт шире
  (8 неразмеченных top-1 против 5 и 6), знаменатель `final_top1` упал до
  16/24, а чувствительных сценариев размечено 4 из 7 — так что высокая доля
  `relevant` 0.938 здесь менее доказательна, чем 0.842 у `max`.
* **Промежуточных режимов имеет смысл ждать немного.** У GLM `low`
  фактически означает «рассуждения нет» (0 reasoning-токенов на 18 из 24
  сценариев), то есть измерены не «low против max», а два края шкалы. Если
  Мария захочет ещё одну попытку по этому кандидату, содержательным будет
  `medium` (≈50% бюджета) — он единственный может дать компромисс между
  35 с/0.649 и 4.4 с/0.516. Из одних наших цифр рекомендовать его нельзя:
  неизвестно, где на шкале лежит порог 0.60 по recall и укладывается ли
  соответствующая задержка в 15 с.
* **Переключение не выполнено.** Конфигурация сервиса этим пакетом не
  менялась: `.env` не редактировался, `AI_SCRIPTURE_REWRITE_MODEL` и
  `AI_SCRIPTURE_RERANK_MODEL` оставлены как были; прод-адаптер под OpenRouter
  не писался (вне скоупа). Rewrite в обоих прогонах читался с диска
  (`--rewrites-file`), rerank в логах обоих прогонов —
  `gemini-3.5-flash-lite`, как и в пакете 86cbbmhk8.

Подзадача зонта 86cbe4mtq «качество подбора Писания на локальных моделях».
Два независимых результата: **инструмент** (генерация `--rewrites-file`

### Инструмент: `gen_rewrites.py`

Раньше артефакты `*_rewrites_v070.json` делались одноразовыми скриптами вне
репозитория — на машине Марии (86cbbm70n) и против OpenRouter (86cbbmhk8).
Протокол при этом описывался словами в README и воспроизводился вручную.
`evaluation/gen_rewrites.py` — тот же протокол кодом, против **любого**
OpenAI-совместимого `chat/completions`:

```bash
python gen_rewrites.py --endpoint <base-url> --model <id> \
    [--api-key K] [--prompt-version 7|8a|8b|8c] [--variants 6] \
    [--temperature 0] [--max-tokens 8192] [--scenarios scenarios.json] \
    [--only id,id] [--timeout 600] --out bench_data/<file>.json
```

- system = инструкция rewrite, user = контекст молитвы, `temperature` (по
  умолчанию 0), `max_tokens` (по умолчанию 8192),
  `response_format={"type":"json_object"}` — как в пакетах 86cbbm70n /
  86cbbmhk8, поэтому артефакты сопоставимы;
- `--max-tokens` — единственная ручка, которую на локальном endpoint **нужно
  опускать**. 8192 перенесены из боевого Gemini-вызова, где потолок съедают
  скрытые reasoning-токены; не-thinking модели на шесть запросов хватает
  ~250 токенов, а на llama.cpp/Ollama с включённым context-shift
  недостижимый потолок превращает вырожденный повтор в **бесконечную**
  генерацию (замерено: несколько сценариев упирались в клиентский таймаут и
  съедали по 12 минут на три попытки). Значение пишется в
  `meta.sampling.max_tokens`, поэтому прогоны с разным потолком видно;
- ретраи те же: невалидный JSON — один повтор, транспорт — до трёх попыток;
- сценарии категории `empty` **пропускаются**: в проде и в бенчмарке они
  обрабатываются безопасным пулом до стадии rewrite (решённый вопрос 5).
  Прежние артефакты содержали их «за компанию» — отсюда 21 сценарий здесь
  против 24 там;
- ключ читается из `--api-key`, иначе из `$REWRITE_BENCH_API_KEY`, иначе из
  `$OPENROUTER_API_KEY`; в файл он не попадает — в `meta.endpoint`
  записывается только схема+хост;
- боевой промпт **не дублируется**: v7 импортируется из
  `app/query_rewrite.py` (`build_rewrite_instruction`,
  `build_rewrite_user_content`, `parse_rewrite_response`). `app/config.py`
  падает без деплойных переменных, поэтому перед импортом скрипт делает
  `setdefault` на заглушки — ровно как `tests/conftest.py`; ни одно из этих
  значений скрипт не читает.

- зависимость ровно одна — **`httpx`** (уже в `requirements.txt`, версия
  контейнера 0.27.0); ни `numpy`, ни venv бенчмарка не нужны, поэтому скрипт
  запускается и на хосте, и внутри `bible-api`;
- **файл пишется после каждого сценария**, атомарно (временный файл +
  `rename`) и ещё раз в `finally`. Это прямое следствие инцидента 2026-09-04:
  прогон писал артефакт только в самом конце, и прерванный (а затем и
  удалённый) прогон v7 не оставил после себя ничего. Прерванный прогон теперь
  оставляет валидный файл, честно помеченный как частичный.

Формат выхода — `bench_data/qwen_rewrites_v070.json` (его и читает
`pipeline --rewrites-file`), плюс поля, которых там не было: `meta.endpoint`,
`meta.prompt_version`/`prompt_revision`, `meta.sampling` (включая
`max_tokens` и `variants`), `meta.partial` / `meta.scenarios_covered` /
`meta.scenarios_expected` / `meta.note`, а по сценарию — `refs` (для 8a/8c),
`reference_leaks` (если в `query` просочилось «глава:стих») и `warning`
(вариантов меньше запрошенного числа).

**Частичный прогон отличим от полного самим кодом.** `meta.partial`
вычисляется, а не проставляется руками: прогон считается полным, только если
запись есть по **каждому** не-`empty` сценарию набора (`scenarios_expected`).
`--only` и любое прерывание автоматически дают `partial=true` и `note` с
предупреждением, что агрегаты несопоставимы с полными артефактами, а
`pipeline --rewrites-file` сочтёт недостающие сценарии отказами rewrite.

**Недобор вариантов пишется в `warning`, а не в `error`** — намеренно:
`retrieval_benchmark._load_external_rewrites` выбрасывает всякую запись с
непустым `error`, так что запись «5 из 6» в `error` молча превратила бы
пригодные варианты в отказ rewrite. `warning` виден в логе прогона и в файле,
но данные сохраняет.

> **Оговорка о сопоставимости `max_tokens`.** У артефактов пакетов 86cbbm70n
> и 86cbbmhk8 (`qwen_rewrites_v070.json`, `glm53flash_*`, `deepseekv4flash_*`)
> блока `meta.sampling` либо нет вовсе (qwen), либо в нём зафиксировано
> `max_tokens: 8192`. Локальные прогоны с `--max-tokens 1024` отличаются от
> них этим параметром. На содержание ответа он влияет только тогда, когда
> модель вырождается в повтор (иначе шесть запросов укладываются в ~250
> токенов), но при сравнении таблиц это нужно держать в голове: строки с
> разным `max_tokens` — не строго один и тот же протокол.

### Версии промптов: `rewrite_prompts.py`

Боевой файл не трогается: v7 берётся из него импортом, а каждая версия 8x
строится **точечной заменой** в этом импортированном тексте. Если якорная
подстрока исчезнет (боевой промпт переписали), сборка падает с явной
ошибкой — молча собрать «похожий» промпт нельзя.

| Версия | Ревизия | Что добавлено к v7 | Гипотеза |
|---|---|---|---|
| `7` | — (боевая, `REWRITE_PROMPT_VERSION = 7`) | ничего, импорт как есть | база |
| `8a` | 1 | ответ — объекты `{"ref": "Книга глава:стих", "query": "..."}`; в артефакт идёт только `query`, ссылка сохраняется в отдельное поле `refs` | малой модели легче вспомнить дословно, если сначала **назвать ссылку**; запрет ссылок внутри запроса сохранён — он просто выполняется отдельным полем, а не подавлением |
| `8b` | **2** | few-shot: по 2 примера «тема + реплики → 6 запросов» на ru/en/uk (все шесть показываются при любом целевом языке) + закрывающее напоминание | модель не понимает, какой **конкретности** от неё хотят, без примеров |
| `8c` | **2** | 8a + 8b (примеры отрисованы в объектной форме) | обе |

**Ревизия 2 у 8b/8c** — закрывающий блок после примеров: язык ответа строго
целевой, примеры показывают только **форму** и копировать их дословно нельзя,
места Писания выбираются под ситуацию, а не те, что в примерах. Повод —
наблюдение пробы: 4B скопировала пример дословно в несоответствующий сценарий
(ниже). Артефакты, снятые на ревизии 1, с ревизией 2 **не сопоставимы** —
поэтому ревизия и пишется в `meta.prompt_revision`.

Инварианты закреплены тестом `tests/test_rewrite_prompts.py` (без БД и сети,
20 проверок): де-фингерпринт сверяется с живым `scenarios.json` — ни одна тема
примера не совпадает с `prayer_context.topic`, ни одно место примера не
совпадает по книге+главе ни с одной ссылкой **любой грады** (коды книг
резолвятся через `app/canon.py`), в текстах `query` нет цифр и названий книг;
плюс `build_instruction("7")` **байт-в-байт** равен
`app.query_rewrite.build_rewrite_instruction` для ru/en/uk, и наличие
закрывающего напоминания после примеров у 8b/8c.

**Де-фингерпринт (обязательное правило, как у промпта reranker'а v6).** Ни
одна тема примеров и ни одно место Писания в них не совпадает с эталоном.
Темы примеров вне набора: экзамен, поиск жилья, публичное выступление,
переезд в другой город, начало учёбы в университете, подготовка к венчанию.
Цитаты написаны по памяти близко к тексту. 36 мест примеров, 34 различные
главы, пересечений с эталонными ссылками — ноль, совпадений тем — ноль.
Это **не утверждение в комментарии, а тест**: каждый пример хранит свою
каноническую пару `(код книги, глава)`, и `tests/test_rewrite_prompts.py`
сверяет их с текущим `scenarios.json` при каждом прогоне pytest — правка
эталона, которая создаст пересечение, уронит тест.

прогон не измеряет.**

Два наблюдения, которых в прежних пакетах не было:

1. **Малая модель ломает сам JSON, и ломает по-разному на разных языках.**
   Отказы распределены крайне неравномерно: uk — 6 из 6 успешных, ru — 5 из
   9, en — **1 из 6**. Поломка стереотипная: массив закрывается фигурной
   скобкой вместо квадратной — `{"queries": [".", "."}}`. Боевой

   `rewrite_failed` с деградацией на сырой запрос. Это **новый** класс риска
   для локальных моделей: у Gemini и у обеих OpenRouter-моделей провайдер
   гарантирует синтаксис (`responseMimeType` / `response_format`), а Ollama
   на OpenAI-совместимом маршруте гарантию не обеспечивает.
2. **Содержательно v7 на 4B — это пересказ слов молящегося, а не Писание.**
   ru-001 («Благодарность за рождение дочки»): «Благодарю Господа, что Он дал
   мне дочь, здоровую и целую», «Господи, я уповаю на Тебя, потому что Ты дал
   мне дочь» — ровно то, что инструкция v7 запрещает («not like the person's
   own words»).

#### Промпт 8a: гипотеза «якорь на ссылку» — предварительно подтверждается

Полного прогона нет. **Сохранено 2 сценария** (ru-002, en-001 —
`..._p8a.json`); ещё 4 отработали в прогоне, лог которого перезаписан, так
что относящиеся к ним наблюдения ниже помечены как непроверяемые. Сигнал
однонаправленный, но доказательная база тонкая — это гипотеза с
подтверждением на двух сценариях, а не результат.

- **JSON перестаёт ломаться** — *наблюдение из утраченного лога, артефактом
  не подтверждено*: ru-001, ru-003, ru-004 (те самые, где v7 отдал невалидный
  JSON) на 8a вернули по 6 вариантов с первой попытки. Проверяемая часть: оба
  сохранённых сценария разобрались с первой попытки (`attempts: 1`).
- **Английский перестаёт быть общими словами** (подтверждается артефактом).
  en-001 на 8a:
  «Do not be anxious about anything, but in everything by prayer and petition,
  with thanksgiving, present your requests to God», «When you pass through the
  waters, I will be with you», «Come to me, all who labor and are heavy laden,
  and I will give you rest», «Trust in the LORD with all your heart and lean
  not on your own understanding», «But those who hope in the LORD will renew
  their strength» — это близкие цитаты, а не благочестивые формулы. На v7 у
  английского была худшая средняя длина в наборе (39.2).
- **Утечек ссылок в `query` не зафиксировано**: модель кладёт ссылку в `ref`,
  как и просили; регэксп-проверка `find_reference_leaks` на всех собранных
  вариантах даёт ноль.
- **Но `ref` у слабой модели часто выдуман.** На русском ru-002 ссылки
  пришли как «Иисусов 1:9-10», «Иисусов 40:1-2» — искажённые названия книг,
  а сами `query` остались общими. То есть якорь помогает ровно настолько,
  насколько модель реально помнит текст: английский корпус она помнит,
  русский и украинский — нет. Поэтому `refs` и сохраняются в артефакте: это
  дешёвый индикатор того, «вспомнила» модель место или сочинила.

#### Промпт 8b/8c: замечен риск дословного копирования примеров

**По 8b данных нет вообще** — до него очередь не дошла. По 8c есть один
сценарий (`..._p8c.json`), и в нём видно следующее.

На 8c (uk-002) один из шести вариантов оказался **дословной копией примера
из промпта** — «Клич до Мене — і Я тобі відповім, і подам тобі великі та
незрозумілі речі, яких ти не знаєш» (пример «початок навчання», Єр. 33:3).
Тема сценария — страх за родных из-за войны, к ней этот стих отношения не
имеет. Это ожидаемая болезнь few-shot у слабых моделей и **измеримая**:
статистика прогона считает долю вариантов, совпадающих с примерами. Для
эталона это безопасно (примеры де-фингерпринтованы, ни одно место не входит
в разметку), но качество подбора такое копирование ухудшает — при полном
прогоне за этой долей нужно следить отдельно.

## Локальные эмбеддеры при хорошем rewrite (ClickUp 86cbe4n7e)

**Дата пакета: 2026-09-04. Эталон `scenarios.json` 0.7.0, пороги
`thresholds.json` 0.3.0, промпт rewrite v7, rerank НЕ запускался.** Подзадача
зонта «качество подбора Писания на локальных моделях» (86cbe4mtq); соседняя
подзадача мерила локальные модели на стадии *rewrite*, эта — на стадии
*эмбеддинга*.

### Гипотеза и почему её стоило проверить

ADR 0002 мерил локальные sentence-transformers по **сырому тексту молитвы** и
получил hit@10 ≤ 0.08 — «на порядок мимо порогов». Но там же, в
диагностическом зонде, зафиксировано: близкая цитата на e5-small встаёт на
1-е место со score 0.9, а переформулированный запрос поднимает Мф 6:25-34 с
ранга ~356 на 4-й. То есть провал ADR 0002 мог быть провалом **формулировки
запроса**, а не эмбеддера, — и с боевой стадией rewrite (которой в ADR 0002
ещё не было) локальные модели могли бы оказаться пригодны. Это не измерялось
ни разу.

Чтобы вклад эмбеддера был изолирован, стадия rewrite во всех прогонах
**заморожена**: берутся переформулировки боевой базы `gemini-3.7-flash`
(промпт v7), извлечённые из `bench_data/pipeline_cache.json` в файл
`bench_data/flash37_rewrites_v070.json` и поданные через `--rewrites-file`.
Это «идеальный rewrite»: между колонками таблиц ниже различается **ровно одна
вещь — модель, которая считает векторы**.

Файл содержит 21 сценарий (24 минус три `empty`: пустую тему бенчмарк и прод
отдают безопасным пулом **до** стадии rewrite), у каждого ровно 6 непустых
вариантов. Извлечение проверено прогоном: с этим файлом и штатным
`--embedder gemini` пайплайн воспроизводит опубликованную базу **побайтово по
метрикам** — 1.000 / 0.789 / 0.664 / 0.004 и те же разбивки по языкам, что в
пакете 86cbbm0vx.

### Опция `--embedder` (чистое расширение `pipeline`)

```bash
python retrieval_benchmark.py pipeline --embedder gemini|minilm|e5-small|e5-base|bge-m3|labse
```

Выбранная модель считает **обе стороны**: и варианты запроса, и корпус
чанков. Дефолт — `gemini`, боевая конфигурация; при нём ни одна существующая
ветка, ни один ключ кэша и ни одна строка label не меняются (суффикс
` embedder=X` дописывается в label только для не-дефолтного значения, как это
уже сделано для `coverage=`).

Локальный путь:

* корпус кэшируется в `bench_data/emb_<model>_title_text.npy` — тот же файл,
  что пишет команда `embed`. Проверка при загрузке общая для всех четырёх
  читателей матриц (`run`, `stores`, обе ветки `pipeline`) и вынесена в
  `load_corpus_matrix`, см. «Матрица корпуса и её отпечаток» ниже;
* префиксы `query:` / `passage:` для e5 берутся из `MODELS`, как в
  `embed_local`; для `bge-m3` добавлена запись `BAAI/bge-m3`, 1024 dims,
  **только dense-голова** (sparse и ColBERT-головы оригинальной модели в
  сравнении не участвуют);
* **про ключ — точная формулировка.** `--embedder` подменяет только стадию
  **эмбеддинга**. Прогон обходится без `GEMINI_API_KEY` тогда и только
  тогда, когда офлайн ещё и стадия rewrite (`--rewrites-file` или
  `--no-rewrite`) **и** не задан `--rerank`. Без этого
  `pipeline --embedder e5-small` дойдёт до `require_rewrite_api_key()` и
  потратит **платный** ключ на каждый сценарий, которого нет в кэше
  `rewrites` — локальный эмбеддер от этого не спасает. Все прогоны пакета
  шли с `--rewrites-file` и без `--rerank`; проверено не рассуждением, а
  tripwire-обёрткой (`require_api_key`, `require_rewrite_api_key`,
  `_key_from_env`, `_query_vector`, `requests.post`, `requests.Session.post`
  подменены на бросающую заглушку) — все завершились `TRIPWIRE OK`. Кэш
  `query_embeddings` локальный путь не трогает (его ключ — хэш текста без
  имени модели, так что общий кэш смешал бы векторные пространства);
* `bge-m3` объявляет контекст 8192 токена — батч из 16 таких на CPU
  выделяет гигабайты активаций. В `LOCAL_ENCODE_LIMITS` для него задано
  `batch_size=4, max_seq_length=512` (длиннее в этом корпусе чанков нет);
  остальные модели сохраняют исторический батч 16 и свой контекст, поэтому ни
  одно ранее снятое измерение не смещается.

Прогоны (венв `evaluation/.venv`: torch 2.14.0+cpu, sentence-transformers
6.0.1, numpy 2.5.2; `app/config.py` валидируется на импорте, поэтому
DB-переменные передаются заглушками — без `--rerank` и `--coverage-translation`
соединения с БД не открывается):

```bash
python retrieval_benchmark.py embed --model bge-m3 --variant title_text --force
python retrieval_benchmark.py pipeline --embedder bge-m3 \
  --rewrites-file bench_data/flash37_rewrites_v070.json \
  --json-out bench_data/results_v070_localemb_bge-m3.json
```

### Матрица корпуса и её отпечаток (побочный фикс этого пакета)

Матрицы `emb_{e5-small,e5-base,minilm}_*.npy`, оставшиеся от ADR 0002,
оказались **устаревшими**: 11 987 строк против 11 960 чанков в нынешнем
`chunks.jsonl` (корпус переэкспортирован 2026-08-24, уже после них).

Опасность здесь не в падении, а в его отсутствии: `corpus[idx] @ qvec`, где
`idx` взят из **новых** метаданных, numpy посчитает молча и вернёт косинусы
**чужих** отрывков. Ровно так цифры ADR 0002 и устарели, никого не потревожив.
А проверять только число строк мало: переэкспорт может сохранить количество и
поменять содержимое.

Поэтому:

* весь доступ к `emb_*.npy` идёт через один хелпер `load_corpus_matrix`,
  который зовут **все четыре** читателя — `run` (`evaluate_config`),
  `stores`, gemini-ветка и локальная ветка `pipeline`. Раньше проверки не
  было ни у одного;
* рядом с матрицей лежит `emb_*.npy.sha1` — sha1 по
  `translation:canonical_id` всех чанков в файловом порядке. Его пишет
  `embed` (и локальная ветка `pipeline`, когда сама считает корпус), а
  `load_corpus_matrix` сверяет;
* несовпадение любого из двух (число строк, отпечаток) — **жёсткая ошибка с
  готовой командой пересборки**, а не тихий пере-эмбеддинг: тот же файл
  читает `run`, и переписать его молча значило бы незаметно изменить чужое
  измерение. Матрица без сайдкара грузится, но печатает предупреждение, что
  проверено только число строк;
* тесты — `tests/test_retrieval_benchmark.py` (без torch и сети): отпечаток
  различает и порядок, и подмену документов при том же количестве; оба
  несовпадения дают `SystemExit`; отсутствие сайдкара даёт предупреждение.

Все пять матриц пересобраны или проштампованы: четыре локальные посчитаны
заново из текущего `chunks.jsonl`, `emb_gemini_title_text.npy` проштампован
без пересчёта (у него совпадает число строк, он датирован тем же экспортом, и
прогон с ним воспроизводит опубликованную базу 1.000 / 0.789 / 0.664 / 0.004
в точности). Отпечаток текущего корпуса — `4bef46fc914b`, 11 960 чанков.

колонок и дарит 3/24 = 0.125 hit@10 даром, так что на общих 24 сравнение
эмбеддеров было бы завышено. Цифры по всем 24 — в артефактах.

Каждая ячейка — отдельный сохранённый прогон, а не строка из чужого stdout;
`config` внутри файла содержит `lexical=off` / `rewrite=off`, по которым
строку и можно опознать:

| строка | артефакт | флаги |
|---|---|---|
| сырой запрос | `results_v070_localemb_<model>_raw.json` | `--no-rewrite --no-lexical` |
| + rewrite v7 | `results_v070_localemb_<model>_nolex.json` | `--no-lexical --rewrites-file …` |
| + rewrite + BM25 | `results_v070_localemb_<model>.json` | боевые дефолты |

| конфигурация (21 сценарий) | gemini | bge-m3 | e5-base | minilm | e5-small |
|---|---|---|---|---|---|
| сырой запрос, только вектор (условие ADR 0002) | 0.286 / 0.090 / 0.102 | 0.238 / 0.065 / 0.051 | 0.095 / 0.025 / 0.029 | 0.095 / 0.024 / 0.014 | 0.143 / 0.041 / 0.062 |
| **+ rewrite v7, только вектор** | **1.000 / 0.681 / 0.616** | **0.857 / 0.356 / 0.453** | **0.571 / 0.226 / 0.290** | **0.524 / 0.169 / 0.267** | **0.381 / 0.144 / 0.191** |
| + rewrite v7 + BM25 (боевой конвейер) | 1.000 / 0.759 / 0.616 | 0.857 / 0.644 / 0.456 | 0.952 / 0.622 / 0.361 | 0.810 / 0.607 / 0.312 | 0.952 / 0.663 / 0.304 |

Первая строка сопоставима с ADR 0002 (с поправкой: там был другой корпус —
11 987 чанков против нынешних 11 960 — и не было ни BM25, ни слияния
вариантов). Обе gemini-ячейки этой таблицы получены **без единого вызова**:
все 126 переформулированных вариантов и все 24 сырых запроса уже лежали в
`query_embeddings` кэша, и оба прогона завершились
«TRIPWIRE OK: every query embedding came from the disk cache» под обёрткой,
блокирующей `requests.post`.

Читается это так:

1. **Гипотеза подтверждается по направлению.** Хороший rewrite поднимает
   локальный эмбеддер из шума в рабочий диапазон: e5-small 0.143 → 0.381
   hit@10 (×2.7), bge-m3 0.238 → 0.857 (×3.6). Приговор ADR 0002 «локальные
   модели проваливают пороги на порядок» вынесен в условиях, в которых
   сегодня прод не работает, и в этом виде он больше не верен.
2. **Но не подтверждается по величине.** Даже при идеальном rewrite лучший
   локальный эмбеддер как эмбеддер даёт 0.857 / 0.356 / 0.453 против
   1.000 / 0.681 / 0.616 у Gemini — по recall почти вдвое хуже.
3. **И заголовочные 0.958 у e5-small/e5-base — не их заслуга.** Добавление
   BM25 двигает e5-small с 0.381 на 0.952 hit@10 (+0.571) и с 0.144 на 0.663
   recall (+0.519), а базу — с 1.000 на 1.000 и с 0.681 на 0.759 (+0.078).
   Ровно то, чего и ждёт ADR 0004: варианты v7 — это близкие цитаты, и
   лексический сигнал находит их **сам, без всякого эмбеддера**. Иными
   словами, e5-small в боевом конвейере проходит два порога из четырёх,
   «спрятавшись за» BM25; его собственный вклад — худший в пакете (0.381), и
   порядок моделей по реальному качеству эмбеддинга обратный табличному:
   **bge-m3 > e5-base > minilm > e5-small**.
4. MRR не лечится ни тем, ни другим: у e5-small BM25 добавляет +0.113 MRR
   (0.191 → 0.304), у bge-m3 — +0.003 (0.453 → 0.456). Ранжирование внутри
   найденного — это ровно та работа, которую делает качество векторов.

### Вердикт

* **Переключать эмбеддер нельзя ни на одну из четырёх моделей.** Все
  проваливают `MRR ≥ 0.60` (лучшая — bge-m3, 0.524, −0.076 до порога и −0.140
  к базе), а `minilm` и `bge-m3` дополнительно проваливают `hit@10 ≥ 0.90`.
  `gemini-embedding-001@768` остаётся боевым; `EMBEDDING_MODEL` /
  `EMBEDDING_DIMENSIONS` не трогались, `app/` не менялся.
* **Но утверждение ADR 0002 о локальных эмбеддерах устарело и должно быть
  переформулировано.** «Проваливают на порядок» относилось к сырому запросу;
  при боевом rewrite лучший локальный эмбеддер отстаёт **примерно вдвое по
  recall и на один порог по MRR**, а не на порядок. Разница между «шумом» и
  «одним непройденным порогом» — это разница между «закрыто» и «есть с чем
  работать».
* **Назначение e5-small резервом в ADR 0002 больше не обосновано, но замены
  ему нет: пригодного резерва при нынешнем железе не существует.** ADR 0002
  выбрал e5-small как «лучшее соотношение RAM/качество среди измеренных» —
  при боевом rewrite он оказывается **худшим** эмбеддером пакета (0.381
  hit@10 своим сигналом), а его табличные 0.958 обеспечены BM25, так что
  основание выбора отпало. Что показал замер вместо этого:
  * **лучший по качеству — `BAAI/bge-m3`** (0.857 / 0.356 / 0.453 своим
    сигналом, единственный локальный, кто где-то обгоняет базу). Цена: 2.25
    ГиБ RSS в прогоне, 3.25 ГиБ при сборке корпуса, ~2 часа CPU на корпус.
    **На прод-VM (2-4 ГБ, там же MySQL) не помещается**;
  * **лучший по соотношению — `e5-base`** (0.571 / 0.226 / 0.290 при 1.42 ГиБ
    RSS): заметно дешевле bge-m3 по памяти, но и качество ниже — до порогов
    не дотягивает так же;
  * **рекомендовать нечего.** Оба варианта либо не разворачиваются, либо не
    проходят, поэтому этот пакет **не назначает новый резерв** — он снимает
    старый. Если независимость от API станет обязательной, вопрос решается
    не выбором модели из этого списка, а железом (память под bge-m3) или
    другим классом решений.
* **Безопасность от эмбеддера не зависит.** `unacceptable@10` = 0.004 во всех
  пяти колонках, включая провальные: чёрный список жанров, diversity и пул
  работают до и помимо векторов. Это ожидаемо (ADR 0004: blacklist не двигает
  метрики, его ценность — гарантия), и это единственный порог, который
  локальные модели берут без оговорок.
* **Что этот пакет НЕ измерял.** Rerank не запускался (по заданию), поэтому
  разделы `final_top1` в артефактах посчитаны только по fallback-политикам и
  по знаменателю 5-8 размеченных из 24 — **недоказательны, в вердикт не
  входят**. Не мерялись: стабильность (по одному сэмплу на модель),
  `labse` (в `MODELS` есть, корпус не считался), sparse/ColBERT-головы bge-m3,
  дообучение под домен и вариант `text` вместо `title_text`.
* **Следствие для соседней подзадачи.** Обе стадии измерены на одном эталоне
  и на одном пороге, и обе локальные замены упираются в разное: локальный
  rewrite (86cbbm70n) терял сам факт попадания в top-10 (hit@10 0.583),
  локальный эмбеддер при хорошем rewrite теряет порядок внутри top-10
  (MRR 0.391-0.524). Комбинация «локальный rewrite + локальный эмбеддер» не
  мерялась и по этим двум замерам не выглядит осмысленной.

### Что дала каждая гипотеза

Разложение по вкладам читается прямо из таблицы: **весь скачок hit@10 даёт
якорь на ссылку (8a), а разницу внутри top-10 добирает few-shot поверх него
(8c).**

| | hit@10 | recall@10 | MRR | средняя длина |
|---|---|---|---|---|
| 7 (боевой) | 0.583 | 0.312 | 0.404 | 58.4 |
| + якорь на ссылку (8a) | **0.875** (+0.292) | 0.496 (+0.184) | 0.490 (+0.086) | 92.1 |
| + few-shot (8b) | 0.667 (+0.084) | 0.361 (+0.049) | 0.447 (+0.043) | 81.3 |
| обе (8c) | **0.875** (+0.292) | **0.547** (+0.235) | **0.558** (+0.154) | 98.6 |

* **Якорь на ссылку — основная механика.** Требование сначала назвать место
  Писания превращает «благочестивую формулу общего содержания» в близкую
  цитату. Пример, `en-001` («Thankful for my new job»): на v7 модель выдаёт
  «I will give thanks to the LORD with all my heart», «The LORD is my
  strength and my shield», «I will walk before the LORD in the land of the
  living» — тот самый режим отказа, который похоронил кандидата в 86cbbm70n;
  на 8a/8c те же шесть слотов заняты «Trust in the LORD with all your heart
  and do not rely on your own understanding», «Do not be anxious about
  anything, but in everything by prayer and supplication…», «Do not fear, for
  I am with you… I will uphold you with my righteous right hand».
* **Few-shot сам по себе слабее и на английском почти не работает.** 8b
  добавляет к v7 всего +0.084 hit@10, и `en-001` на нём остаётся набором
  общих формул («I will bless the LORD at all times»). Длину он поднимает
  (58 → 81), а конкретность — нет.
* **Сумма не аддитивна, но и не отменяет слагаемые.** hit@10 у 8c ровно
  такой же, как у 8a (0.875) — «попадание в десятку» уже вытянуто якорем;
  зато recall (+0.051 к 8a) и MRR (+0.068 к 8a) растут, то есть примеры
  добирают *остальные* релевантные окна и поднимают их выше.

#### Выдуманные ссылки: у 30B их нет

`refs` (поля 8a/8c, 126 ссылок в каждом) сверены с 66-книжным каноном
`app/canon.py`: **126/126 в обоих файлах называют реальную книгу и
существующую в ней главу**, ноль неразобранных, ноль невозможных глав. Модель
пишет названия по-английски (`Psalm`, `Isaiah`, `Matthew`, `Philippians`,
`Jeremiah`, `Proverbs`, …) при любом целевом языке запроса. Это ровно та
разница с 4B из пробы 86cbe4nd3, где на русском приходили искажённые
«Иисусов 1:9-10»: у 30B якорь работает не как самообман, а как настоящее
воспоминание места.

Дополнительный (не пороговый, диагностический) замер: доля `refs`, попадающих
по паре «книга + глава» в **размеченные relevant-ссылки** сценария —
**8a 30/126 (0.238)**, **8c 37/126 (0.294)**; хотя бы одна такая ссылка есть
у **17 из 21** сценария в обоих файлах. То есть модель во многих случаях
называет именно то место, которое эталон считает правильным, — и потеря
происходит дальше, на пути «цитата по памяти → эмбеддинг → окно чанка».

Утечек «глава:стих» внутрь текста запроса нет ни в одном из четырёх файлов
(`find_reference_leaks` даёт ноль на всех 503 вариантах пакета).

### Финальный top-1: измерен только для p7, и это провайдерский инцидент

**Стадию rerank этот пакет не смог довести до конца.** С 15:30 до 18:00 MSK
2026-09-04 `gemini-3.5-flash-lite` (и `gemini-3.1-flash-lite`) отвечали
`503 UNAVAILABLE` «This model is currently experiencing high demand» и
read-таймаутами, при том что `gemini-3.7-flash` тем же ключом отвечал `200` —
то есть это была деградация конкретных lite-моделей, а не наш ключ и не наша
сеть. Прогон бенчмарка на такой отказ реагирует штатно: сценарий, чей вызов
rerank не прошёл три попытки, уходит в `fallback_rank1` (в проде это
`fallback_reason=rerank_failed`), и в артефакте у него стоит
`method: "fallback_rank1"`. К 18:01 ключ упёрся в **дневную** квоту:

```
"quotaId": "GenerateRequestsPerDayPerProjectPerModel-FreeTier",
"quotaValue": "500", "model": "gemini-3.5-flash-lite"
```

Это ровно тот случай, ради которого в `app/gemini_retry.py` читается `quotaId`,
а не `retryDelay` (тело обещало «retry in 19s»): суточная квота не откроется
до завтра. По заданию ретраями ключ не жёгся — пакет остановлен здесь.

### Вердикт

* **Против критерия зонта ни один промпт не проходит.** Лучший — **8c**:

  Три порога из четырёх не взяты, `unacceptable@10` взят (0.004).
  Переключать `AI_SCRIPTURE_REWRITE_MODEL` на локальную модель по-прежнему
  нельзя; `.env` не трогался, `app/` не менялся.
* **Но вывод пакета 86cbbm70n «локальная модель проваливает с большим
  отрывом» относился к промпту, а не к модели.** На боевом v7 та же

  и теряла эталон из top-10 у **10 сценариев из 24**; на 8c отставание —
  0.025 / 0.053 / 0.042, а без relevant в top-10 остаются **три**. Это
  разница между «закрыто» и «одна итерация промпта до порогов».
* **Работает якорь на ссылку, а не примеры.** 8a даёт весь прирост hit@10
  (+0.292), 8b — только +0.084; сумма 8c поднимает recall и MRR ещё на
  0.051 / 0.068 к 8a. Плюс якорь **снимает** главный побочный эффект
  few-shot: доля вариантов, списанных с примеров, — 0.112 у 8b против 0.008
  у 8c при тех же примерах в промпте. Ссылки 30B при этом настоящие:
  126/126 существующих книг и глав в обоих файлах.
* **`final_top1` не измерен и остаётся открытым** (см. выше: 503 на
  lite-моделях, затем исчерпанная дневная квота 500 запросов). Полный ответ
  требует повторного прогона 8a/8b/8c с `--rerank` на свежей квоте; кэш

## Инструмент замера локального rerank (ClickUp 86cbed851)

Подзадача зонта 86cbe4mtq «качество подбора Писания на локальных моделях».
Здесь только **инструмент**: цепочка, которой любая OpenAI-совместимая
модель отвечает на стадию финального выбора, а бенчмарк считает по её
ответам обычный отчёт `final_top1`. Замеров качества локальной модели в этой
подсекции нет — полную матрицу снимает отдельный прогон на сервере Марии
(команды ниже).

**Зачем.** Предыдущие подсекции измеряли локальную модель на стадии
**rewrite** — вспоминании подходящих мест по памяти; там 30B не добрала до
порогов (86cbea05x), а локальные эмбеддеры оставили MRR ниже порога
(86cbe4n7e). Гипотеза зонта: **выбрать лучший из десяти готовых текстов
проще, чем вспомнить**, и именно rerank — стадия, где локальная модель может
дотянуть до прода. Проверять это нужно тем же промптом v9, теми же
кандидатами и тем же отчётом, что у Gemini, иначе сравнение ничего не значит.

### Три шага

**Файлы ходят между хостом и контейнером на каждом шаге** — `evaluation/`
только копируется в `bible-api`, не смонтирован, поэтому `docker cp` в обе
стороны обязателен:

```bash
# 1. Экспорт входов reranker'а из ЗАПИСАННОГО прогона (нужны БД и корпус,
#    поэтому шаг идёт в контейнере) и возврат артефакта на хост
docker cp evaluation/. bible-api:/code/evaluation
docker exec -w /code/evaluation bible-api python3 retrieval_benchmark.py \
  export-rerank-input \
  --results bench_data/results_v070_rewrite_flash37.json \
  --out bench_data/rerank_input_flash37.json
docker cp bible-api:/code/evaluation/bench_data/rerank_input_flash37.json \
  evaluation/bench_data/

# 2. Ответы модели (запускается там, где виден endpoint — например на хосте;
#    нужен только httpx, ни numpy, ни БД)
cd evaluation
python gen_reranks.py --endpoint http://<host>/v1 --model <id> \
  --input bench_data/rerank_input_flash37.json \
  --out bench_data/qwen30b_reranks_flash37.json

# 3. Ответы — обратно в контейнер, и прогон бенчмарка по ним
docker cp evaluation/bench_data/qwen30b_reranks_flash37.json \
  bible-api:/code/evaluation/bench_data/
docker exec -w /code/evaluation bible-api python3 retrieval_benchmark.py \
  pipeline --rewrite-model gemini-3.7-flash \
  --reranks-file bench_data/qwen30b_reranks_flash37.json \
  --json-out bench_data/results_v070_localrerank_qwen30b_flash37.json
docker cp bible-api:/code/evaluation/bench_data/results_v070_localrerank_qwen30b_flash37.json \
  evaluation/bench_data/
```

**Шаг 1 берёт кандидатов из артефакта прогона, а не пересчитывает retrieval.**
`details[].top` записанного `--json-out` — это ровно тот список, который
конкретный прогон подал reranker'у, поэтому экспорт воспроизводит стадию
**того самого** прогона. Отсюда и требование к шагу 3: конфигурация прогона
должна совпадать с той, из которой сделан экспорт (для `results_v070_rewrite_flash37.json`
это `--rewrite-model gemini-3.7-flash`, для артефактов с локальным rewrite —
тот же `--rewrites-file`).

Сценарии категории `empty` (`ru-009`, `en-006`, `uk-006`) в экспорт не
попадают: их отдаёт безопасный пул **до** стадии rerank, поэтому в файле 21
запись, а не 24 — та же арифметика, что у `gen_rewrites.py`. В прогоне они
по-прежнему участвуют и по-прежнему дают top-1 из пула.

### Форматы файлов

`rerank_input_<src>.json` — то, что получает боевой `GeminiPassageReranker`:

| Поле сценария | Что это |
|---|---|
| `instruction` | системная инструкция v9, `passage_rerank.build_rerank_instruction(count, key_verses)` |
| `user_content` | контекст молитвы + нумерованные кандидаты с маркерами `[n]`, `build_rerank_user_content` |
| `response_schema` | JSON-схема ответа, `build_rerank_response_schema` |
| `candidate_count` | сколько кандидатов (верхняя граница номера) |
| `candidates` | `number`, `canonical_id`, `translation` и координаты каждого |
| `candidates_hash` | идентичность списка кандидатов — **тот же хэш, что в ключе кэша `reranks`** |
| `key_verses` | был ли доступен построчный текст: без БД кандидаты идут без маркеров, и контракт ключевых стихов выпадает из инструкции и из схемы — ровно как деградирует прод |

`meta` артефакта хранит `source_results` и `source_config` (из какого прогона
сделан), `rerank_prompt_version`, `scenarios_version` и
`partial`/`scenarios_covered`/`scenarios_expected`.

Промпты **не переписаны** — они строятся боевыми функциями `app/passage_rerank.py`.
Это проверено двумя способами: тестами (`tests/test_retrieval_benchmark.py`
сверяет `user_content`/`instruction`/`response_schema` с боевыми функциями и
в варианте с маркерами, и без) и живой сверкой — прогон `pipeline` с
подменённым `_rerank_cached`, записывающим фактические аргументы боевого
вызова, дал **21/21 побайтовое совпадение** по обоим экспортам
(`flash37` и `qwen30b_p8c`) при нулевых вызовах провайдера.

Тексты кандидатов рендерит **одна** функция —
`retrieval_benchmark.candidate_prompt_text`, которую зовут и `pipeline
--rerank`, и `export-rerank-input` (по ревью: раньше у каждой ветки была своя
копия, а побайтовое равенство держалось только на совпадении копий).
Отдельный тест сверяет её вывод с боевым `retrieval._candidate_prompt_text`
на одном и том же чанке — и с маркерами `[n]`, и в деградированном варианте
без построчного текста.

`<model>_reranks_<src>.json` — ответы модели, вход `--reranks-file`:
по сценарию `chosen_index` (**0-based**, как индекс в списке кандидатов),
`key_verse_span` (`[start, end]` маркеров или `null`), `reason`, `raw`
(усечённый сырой ответ), `latency_ms`, `attempts`, `error`,
`chosen_canonical_id` (для чтения глазами) и скопированный `candidates_hash`.

- ответ разбирается **боевым** `parse_rerank_response(text, candidate_count)`:
  номер вне диапазона, поломанный JSON, отсутствующий `candidate` — ошибка
  ровно там же, где она была бы в сервисе, и в файл такой выбор не попадает;
- испорченный диапазон ключевых стихов ошибкой **не** считается (ADR 0005):
  выбор отрывка остаётся, подсветка пропадает, в запись пишется `warning`.
  То же на стороне чтения: `--reranks-file` принимает `key_verse_span` только
  как пару целых, всё остальное (в том числе диапазон из одного элемента)
  молча означает «без подсветки» и прогон не роняет;
- **в `error` пишется только категория отказа** — тип исключения и, для
  HTTP-ошибки, статус (`transport: HTTPStatusError (HTTP 429)`). Сообщение
  провайдера в файл не попадает намеренно: httpx вставляет в него полный URL
  запроса вместе с query-строкой, а там у части endpoint'ов лежит ключ, —
  файлы же коммитятся в публичный репозиторий. Та же правка сделана и в
  `gen_rewrites.py` (тесты `tests/test_gen_reranks.py`,
  `tests/test_gen_rewrites.py`);
- протокол тот же, что у `gen_rewrites.py`: `temperature 0`,
  `response_format=json_object`, невалидный ответ — один повтор, транспорт —
  до трёх попыток, атомарная запись файла после **каждого** сценария,
  `meta.partial` вычисляется кодом, ключ в файл не попадает (в `meta.endpoint`
  только схема+хост);
- `response_schema` в запросе **не отправляется** — локальные серверы понимают
  `json_object`, а настоящая защита всё равно серверная (боевой парсер).

### Что делает `--reranks-file`

- **`GeminiPassageReranker` не создаётся вообще** — флаг подразумевает стадию
  финального выбора и отвечает на неё с диска. Прогон tripwire-совместим:
  подмена `passage_rerank.GeminiPassageReranker.__init__` на выбрасывающую
  заглушку его не роняет (проверено и живьём, и тестом). Ключ Gemini **для
  стадии rerank** не нужен; `--rerank` и `--reranks-file` взаимоисключающи
  на уровне CLI — один прогон отвечает на эту стадию одним способом.
- **Но прогон целиком бесплатным от этого не становится.** При дефолтном
  `--embedder gemini` ключ по-прежнему требуется — им открывается даже чтение
  кэша эмбеддингов (`_pipeline_embedder` спрашивает его до кэша), а без
  `--rewrites-file`/`--no-rewrite` каждый промах кэша rewrite — это платный
  вызов `gemini-3.7-flash`. Полностью безвызовный прогон, как и раньше, — это
  локальный `--embedder` плюс оба офлайн-флага (см. врезку «Внимание, деньги»
  выше).
- Ответ берётся по id сценария **при совпадении `candidates_hash`**.
  Несовпадение — жёсткая ошибка с текстом, называющим сценарий, оба хэша и
  способ починки: ответ — это индекс в конкретный список, на другом списке он
  указывает на другой отрывок. **Отсутствие поля `candidates_hash` — тоже
  жёсткая ошибка**: непроверяемому ответу не верят, иначе удаление одного
  поля обходило бы защиту. Тихой деградации здесь нет намеренно.
- Запись с `error`, запись без пригодного `chosen_index` и сценарий, которого
  в файле **нет**, уходят в ту же ветку, что живой `PassageRerankError`:
  fallback «ранг-1 retrieval», счётчик `failures` (отсутствующие считаются
  отдельно и печатаются в строке `rerank:`). Это то, что делает прод, и это
  же позволяет пробный прогон по подмножеству (`--only`).
- Отчёт `final_top1` и таблица подсветок работают как обычно; кэш `reranks`
  **не читается и не пишется**.
- Метка прогона получает суффикс `rerank=file:<model>` (по образцу
  `rewrite=file:...`). Без флага метка не меняется ни на байт — прежние
  артефакты остаются сопоставимыми.

### Команда для агента на сервере Марии

**Где взять входы.** Два файла — `rerank_input_flash37.json` (кандидаты
боевого конвейера) и `rerank_input_qwen30b_p8c.json` (кандидаты лучшего
локального rewrite из 86cbea05x) — сняты 2026-09-04 и лежат в
`evaluation/bench_data/` **на локальной машине оркестратора**. В git они не
входят (воспроизводимы, см. `.gitignore`), поэтому на другой машине их либо
получают шагом 1 самостоятельно — для этого нужны `cep_public`,
`bench_data/chunks.jsonl` и соответствующий `results_*.json`, — либо
оркестратор прикладывает их к тикету. Дальше нужны шаги 2 и 3:

```bash
# 2. два файла ответов (там, где виден endpoint 30B)
cd evaluation

# 3. прогоны бенчмарка (конфигурация обязана совпадать с источником экспорта!)

docker cp bible-api:/code/evaluation/bench_data/results_v070_localrerank_qwen30b_p8c.json \
```

Сравнивать: первый прогон — с базовой колонкой
`results_v070_rewrite_flash37.json` (тот же retrieval, отличается только
модель rerank: **чистое** сравнение reranker'ов), второй — с
`results_v070_rewrite_qwen30b_p8c.json` (полностью локальный конвейер).

Оговорки для прогона:

- **`--max-tokens` по умолчанию 2048**, и это не та ручка, что в
  `gen_rewrites.py`: ответ rerank'а — три числа и одна фраза, вырожденного
  повтора здесь не бывает. Опускать значение нужды нет, поднимать — только
  для «думающей вслух» модели;
- **контекст модели.** Промпт rerank'а — это 10 отрывков целиком, ~5-6 тысяч
  токенов. На Ollama с дефолтным `num_ctx 4096` сервер отвечает `400
  exceed_context_size_error`, и это выглядит как транспортная ошибка. Нужен
  endpoint с окном ≥ 8k (для Ollama — производная модель:
  `FROM <model>` + `PARAMETER num_ctx 8192`, затем `ollama create`);
- задержка на длинном промпте заметно выше, чем у rewrite: считать бюджет
  прогона по 21 сценарию, а не по одному;
- **суженный пул `npu` (ADR 0007) — это другой список кандидатов**, поэтому
  `--coverage-translation 21` требует своего экспорта (из
  `results_..._npu_coverage.json`) и своего файла ответов; подложить сюда
  ответы основного прогона нельзя — остановит проверка `candidates_hash`;
- гейт `ungraded_review_required` открывается так же, как у прежних пакетов:
  чужая модель уводит top-1 в неразмеченные отрывки, и доли по меньшему
  знаменателю **не сопоставимы** с базой напрямую.

## Локальный rerank на qwen3-30b: замер качества (ClickUp 86cbedqvr)

Подзадача того же зонта 86cbe4mtq. Предыдущая подсекция дала **инструмент**
(86cbed851); здесь — **замер**: те же 24 сценария, тот же промпт v9, тот же
отчёт `final_top1`, но на стадии финального выбора отвечает
`qwen3-30b-a3b-instruct-2507` с сервера Марии, а не Gemini.

Гипотеза зонта: «выбрать лучший из десяти готовых текстов проще, чем
вспомнить». Она проверяется двумя прогонами, и разница между ними — весь
смысл пакета:

* **A — локальный rerank поверх Gemini-кандидатов.** Retrieval прод-качества
  (rewrite `gemini-3.7-flash`), меняется ровно одна стадия. Это **чистое**
  сравнение reranker'ов.
* **B — полностью локальная связка.** Rewrite из лучшего локального промпта
  8c (86cbea05x) плюс локальный rerank. Это то, что реально получил бы
  пользователь на self-hosted конвейере.

### Прогоны

Совпадение индексов низкое (5 из 21), но **цена расхождений почти нулевая**:
на 16 сценариях, размеченных в прогоне A, база даёт relevant 0.938 и 30B
даёт ровно 0.938 — паритет с одним понижением и одним повышением. Различие
целиком в `sensitive`: на шести размеченных чувствительных сценариях база —

предпочитать присутствие Божие, а не обещания физической безопасности»), —
то есть 30B не нарушает жёсткую границу `unacceptable`, но хуже держит
редакторское предпочтение внутри `relevant`/`acceptable`.

Колонка B от базы отличается тем, что **база сама неполна**: в
`results_v070_rewrite_qwen30b_p8c.json` 6 из 21 сценариев выбраны

односторонне выгодно локальной модели и приводится справочно; пороговые
числа B в таблице выше стоят сами по себе.

### Подсветка ключевых стихов

Подсветка есть в 19 из 24 сценариев в обоих прогонах. Три отсутствия в
каждом — сценарии категории `empty` (`ru-009`, `en-006`, `uk-006`): их
отдаёт безопасный пул до стадии rerank, подсветки там нет по устройству.
Реальных промахов по два на прогон, и они **разной природы**:

| прогон | сценарий | что вернула модель | почему подсветки нет |
|---|---|---|---|
| A и B | en-005 | `key_verse_start: 13, key_verse_end: 16` | диапазон из 4 стихов, контракт ADR 0005 — 1-3; боевой `parse_rerank_response` отбрасывает его ещё при генерации ответов, в файле стоит `warning: no usable key-verse span in the answer` |
| B | uk-004 | `5 … 8` | то же — 4 стиха |
| A | ru-003 | `10 … 10` | диапазон формально валиден и в файл попал, но выбран отрывок Откр 7:9-17 — в нём **девять** стихов, маркера `[10]` не существует; подсветка отваливается уже на стадии разрешения координат, `warning` в файле ответа нет |

Оба режима отказа безвредны по контракту (выбор отрывка сохраняется,
пропадает только подсветка) и оба воспроизводят поведение прода. Второй
режим стоит знать при чтении файлов ответов: `*_reranks_*.json` проверяет
**форму** диапазона, а не его попадание в число стихов выбранного кандидата.

### Вердикт против критерия зонта

**Ни (а), ни (б) порогов `final_top1` не проходят.** В обоих прогонах падает
`sensitive_relevant_share` (0.833 и 0.500 при пороге 1.0) и открыт гейт
`ungraded_review_required` (по 8 неразмеченных top-1).

Но провалы разного веса, и это главный результат пакета:

* **(а) поверх Gemini-кандидатов локальный rerank держится вплотную к
  проду.** `unacceptable` — ноль, `relevant-or-acceptable` — 1.000,
  эталонная ловушка en-005 не выбрана, а на общем размеченном подмножестве
  из 16 сценариев relevant совпадает с Gemini до третьего знака (0.938
  против 0.938). Единственное размеченное расхождение вниз — uk-002, и оно
  внутри `relevant` → `acceptable`, а не к небезопасному выбору. С точностью
  до неразмеченного остатка это **паритет**, и закрыть вопрос может только
  разметка Марии.
* **(б) полностью локальная связка заметно слабее** — relevant 0.812,
  sensitive relevant 0.500 — но ухудшение приходит **не от rerank**: те же
  ответы той же модели на худших кандидатах дают худший результат, а
  retrieval-пороги провалены ещё до стадии выбора (hit@10 0.875, recall
  0.547, MRR 0.558).

**Узкое место — rewrite.** Гипотеза зонта («выбрать проще, чем вспомнить»)
подтвердилась: на стадии финального выбора локальная 30B практически
догоняет Gemini, тогда как на стадии rewrite та же модель не добрала до
retrieval-порогов ни одним из четырёх промптов (86cbea05x), а локальные
эмбеддеры оставили MRR ниже порога (86cbe4n7e). Порядок работ для
self-hosted конвейера: сначала rewrite (или замена стадии на что-то, не
требующее вспоминания мест по памяти), потом эмбеддинги, и только потом —
если понадобится — rerank.
