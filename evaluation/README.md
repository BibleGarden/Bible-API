# Scripture Selection Benchmark

Эталонный набор для оценки качества серверного RAG-подбора мест Писания под
контекст молитвы (тема + разрешённые ответы пользователя из диалога Twinkler).
Тикет: ClickUp 86cb8vvyb. Статус: **approved** (версия 0.2.0) —
богословская/редакторская проверка завершена 2026-08-24, все 24 сценария
`review_status: approved`, набор утверждён Марией. Новые сценарии добавляются
со `review_status: draft` до утверждения.

Директория `evaluation/` выбрана потому, что в репозитории нет каталога
бенчмарков: `tests/` содержит pytest-тесты сервиса, `architect/` — документацию
архитектуры. Набор — это данные, а не тесты, поэтому он живёт отдельно;
pytest-тест схемы лежит в `tests/` и попадает в общий прогон.

## Система координат (важно)

Ссылки на Писание — только числовые координаты
`book_number / chapter / verse_start / verse_end`.

- `book_number` — `cep_public.bible_books.number`, славянский порядок канона
  1–66: Быт=1, Пс=19, Мф=40, **Иак=45, 1Пет=46 … Рим=52** (соборные послания
  раньше павловых), Откр=66.
- **Псалтирь неоднородна по переводам.** Канон набора —
  `english-masoretic`: масоретские номера псалмов, надписания не нумеруются
  (как в `bsb`/`webus`/`webbe`). Фактическая нумерация в БД:
  - `syn`, `bti`, `npu` — септуагинтская нумерация глав, надписания посчитаны
    как стихи;
  - `ubh` — масоретские главы, но надписание = стих 1 (еврейская нумерация);
  - `bsb`, `webus`, `webbe` — канон набора, без сдвигов.

  Следствие: при резолве координат Псалтири для не-английских переводов
  **обязателен слой маппинга** (глава и стих). Это зафиксировано в
  `coordinate_system.psalm_mapping_required` (вопрос №1 в «Решённых вопросах»).
  Маппинг реализован проектно: `app/versification.py` + таблица
  `cep_public.psalm_verse_mappings` (ADR 0003); бенчмарк использует именно
  его (`retrieval_benchmark.load_psalm_maps`).
- **Покрытие переводов**: `npu` содержит только 28 книг (часть ВЗ + НЗ);
  полные Библии — `syn`, `bti`, `bsb`, `webus`, `webbe`, `ubh`. Проверка
  существования координат для украинского языка идёт по `ubh`.

## Формат сценария

```json
{
  "id": "ru-001",                  // ^(ru|en|uk)-\d{3}$, префикс = language
  "language": "ru",
  "category": "regular",           // regular|ambiguous|short|empty|sensitive
  "review_status": "draft",        // draft | approved (ставит рецензент)
  "prayer_context": {
    "topic": "…",                  // тема молитвы; "" только для category=empty
    "user_replies": ["…"]          // разрешённые ответы пользователя Twinkler
  },
  "notes": "заметка для рецензента (по-русски)",
  "references": [
    {"book_number": 19, "chapter": 127, "verse_start": 3, "verse_end": 5,
     "grade": "relevant", "reason": "почему такая оценка"}
  ]
}
```

Каждый сценарий содержит минимум 3 ссылки, среди них обязательно есть
`relevant` и `unacceptable`. Категории:

- `regular` — обычные темы (благодарность, работа, семья, прощение);
- `ambiguous` — неоднозначные темы («свет», «мир», «дорога», «отец»);
- `short` — сверхкороткие запросы (1–2 слова);
- `empty` — тема отсутствует (пустая строка, пустые ответы);
- `sensitive` — чувствительные состояния (горе, болезнь, тревога/паника,
  война, одиночество, ощущение никчёмности).

Важно: набор ссылок **не исчерпывающий** — в корпусе есть другие столь же
уместные отрывки, не попавшие в разметку. Поэтому метрики трактуются как
нижняя граница, а неразмеченный top-1 отправляется на ручную оценку
(`ungraded_review_required`).

## Критерии качества

Шкала ручной оценки совпадает со шкалой град в данных — 3 грады, без
промежуточных баллов (решение Марии, 2026-08-24):

| Града | Описание |
|-------|----------|
| relevant | Прямо отвечает теме и состоянию, целостен, бережен по тону |
| acceptable | Не противоречит теме, поддерживает молитву, но более общий/смещённый |
| unacceptable | Искажает смысл, звучит как обвинение/угроза/проклятие, лексическая ловушка, нет молитвенной ценности |

Пограничный случай («формально по теме, но натянуто») решается рецензентом
в пользу `acceptable` или `unacceptable`; в состоянии сомнения — понижать.
К каждой ручной оценке обязательно прилагается свободное текстовое поле
«почему» — краткое обоснование грады; оно используется для отладки промптов
и анализа промахов (в эталоне соответствует полю `reason`).

Аспекты, которые обязан проверить оценщик:

1. **Уместность** — отвечает ли отрывок теме и эмоциональному состоянию
   (не только ключевым словам). Лексическое совпадение при противоположном
   смысле («мир»/«не любите мира», «peace»/«not peace, but a sword») = 0.
2. **Контекстная целостность** — не вырван ли фрагмент из контекста так, что
   смысл искажается: слова друзей Иова, проклятия завета, нарративные
   эпизоды, гиперболы («возненавидь отца»), обещания конкретным адресатам.
3. **Тон и чувствительность** — в состояниях горя/болезни/кризиса недопустимы
   отрывки, читающиеся как обвинение, объяснение причины страдания или
   усиливающие отчаяние. Для category=sensitive любые сомнения = понижение.
4. **Целостность отрывка** — диапазон стихов образует законченную мысль
   (не обрывается посреди предложения, не начинается с «поэтому» без опоры).
5. **Разнообразие и повторы** (свойство системы, не отрывка) — в окне из N
   последовательных выборов не повторяется один и тот же отрывок и не
   доминирует одна книга; пороги — в `thresholds.json` (`diversity`).

## Метрики

Совпадение кандидата с эталонной ссылкой: равенство `book_number` и
`chapter` + пересечение диапазонов стихов (см. `matching_rule` в
`thresholds.json`).

Retrieval (top-K кандидатов до финального ранжирования):

- **hit_rate@K** — доля сценариев, где в top-K есть хотя бы одна `relevant`
  ссылка;
- **recall@K** — средняя по сценариям доля размеченных `relevant`, попавших в
  top-K (макро-усреднение);
- **MRR** — средний обратный ранг первой `relevant` ссылки;
- **unacceptable_share@K** — средняя доля `unacceptable` среди top-K.

Финальный выбор (top-1, то, что увидит пользователь):

- **relevant_share** — доля сценариев с top-1 = `relevant`;
- **relevant_or_acceptable_share** — доля сценариев с top-1 `relevant` или
  `acceptable`;
- **unacceptable_share** — доля сценариев с top-1 = `unacceptable`;
  требование тикета: **строго 0**, отдельно контролируется на
  category=sensitive;
- **sensitive_relevant_share** — доля sensitive-сценариев с top-1 =
  `relevant`; требование (ужесточение, согласовано 2026-08-24): **строго
  1.0** — для category=sensitive top-1 обязан иметь граду `relevant`,
  `acceptable` недостаточно (`sensitive_relevant_share_min` в
  `thresholds.json`);
- top-1, не попавший в разметку, оценивается вручную по 3-градовой шкале
  выше (с обязательным «почему») и без конвертации вливается в набор как
  новая града (пополнение разметки — часть процедуры прогона).

Разнообразие: прогон одного сценария N раз (или N дней подряд) — метрики
повторов и распределения по книгам в окне `no_repeat_window_selections`.

## Пороги

Значения — в `thresholds.json` (отдельный файл, чтобы согласование
порогов не смешивалось с правками разметки). Логика выбора: сначала жёсткая
безопасность (ноль явно неуместных в top-1; для sensitive top-1 строго
`relevant`), затем полезность (`relevant_or_acceptable >= 0.95`,
`relevant >= 0.70`), затем качество retrieval, достаточное для работы
ранжирования (`hit_rate@10 >= 0.90`, `MRR >= 0.60`).

**Статус: approved (версия 0.2.0)** — пороги согласованы Марией
2026-08-24: черновые значения приняты как есть, добавлено одно ужесточение —
`sensitive_relevant_share_min = 1.0` (для sensitive-сценариев top-1 обязан
быть `relevant`).

## Процедура ручной оценки

1. Рецензент читает сценарий (тему и ответы) на языке сценария.
2. Для каждой ссылки открывает отрывок в переводе соответствующего языка
   (для Псалтири — с учётом маппинга нумерации) и проставляет граду по
   3-градовой шкале (`relevant` / `acceptable` / `unacceptable` — та же,
   что в данных, без промежуточных баллов) **и обязательно заполняет
   свободное текстовое поле «почему»** — краткое обоснование грады
   (служит для отладки промптов и анализа промахов).
3. Расхождение с текущей градой — правка грады + `reason`; спорные случаи
   помечаются в `notes` и решаются Марией. Ручные оценки вливаются в
   эталон без конвертации — как новые грады.
4. После проверки сценария: `review_status: approved`.
5. Когда все сценарии approved: `status: approved`, `approved_by`, bump
   минорной версии.

## Версионирование

- patch (0.1.x) — опечатки, уточнение reason/notes без смены град;
- minor (0.x.0) — изменение град, добавление/удаление сценариев или ссылок;
- major — изменение схемы или системы координат.

Правки согласуются через ревью; файл живёт в git вместе с кодом.
