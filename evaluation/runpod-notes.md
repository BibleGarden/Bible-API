# Runpod: практические заметки по GPU-экспериментам

Проверено 2026-09-12 в эксперименте
[86cbh0p8t](https://app.clickup.com/t/86cbh0p8t): Gemma 4 31B FP8 на одной
Runpod L40S 48 ГБ. Полный протокол и измерения лежат в
[`bench_data/runpod_86cbh0p8t/`](bench_data/runpod_86cbh0p8t/).

## Подготовка и стоимость

- До создания Pod проверить живой остаток бюджета, цену нужной GPU и её наличие
  в подходящем дата-центре. Каталог меняется; наличие карты в списке не означает
  свободную карту в выбранной зоне.
- Проверенная 2026-09-12 схема MCP `create-pod` не имела поля срока жизни.
  Дедлайн остановки ведётся снаружи и проверяется отдельно; перед новым опытом
  сверить актуальную схему, а не добавлять выдуманный параметр.
- Для короткого одноразового опыта подходит обычный Pod volume: после копирования
  результатов Pod удаляется целиком. В этом опыте после удаления Pod повторная
  проверка показала `pods=[]`, `networkVolumes=[]`; оплачиваемых дисков не осталось.
- Остановка сохраняет Pod volume и продолжает тарификацию. На 2026-09-12 60 ГБ
  стоили $12/месяц; отдельный network volume такого объёма — около $4.20/месяц.
  Перед новым запуском цены нужно снять заново. Сохранять диск имеет смысл лишь
  для согласованной серии повторных опытов.
- 30 ГБ container disk в этом запуске занял около 300 МБ. Эта цифра описывает
  writable layer и ничего не говорит о размере скачанных слоёв образа; по ней
  нельзя выводить безопасный минимальный размер диска.

## Холодный запуск

- Закреплённый `vllm/vllm-openai:v0.24.0` для linux/amd64 содержал 8.572 GiB
  сжатых слоёв и на холодном хосте скачивался 72 минуты 54 секунды. Статус
  `RUNNING` означал состояние Pod, а не готовность API.
- Официальный PyTorch-шаблон даёт готовую среду разработки, но не обещает, что
  образ закеширован на конкретном хосте. Network volume хранит данные модели и
  cache, но не устраняет холодное скачивание Docker-образа.
- Веса `RedHatAI/gemma-4-31B-it-FP8-dynamic` скачались за 206 секунд. После этого
  vLLM ещё загружал checkpoint, компилировал kernels 87 секунд и захватывал CUDA
  graphs около 15 секунд. Готовность подтверждается только аутентифицированным
  внешним `GET /v1/models` и реальным completion-запросом.
- Для повторяющейся долгой серии имеет смысл вынести Hugging Face cache и, если
  runtime это поддерживает, compilation cache в постоянный том. Для текущего
  одноразового опыта пользователь решил удалить диски.

## Совместимость и память

- Ada и FP8 сами по себе не гарантируют одинаковый runtime. vLLM выбрал
  `CutlassFP8ScaledMMLinearKernel`, а из-за неодинаковых размеров attention heads
  Gemma — backend `TRITON_ATTN`. Это нормальный выбор runtime, который надо
  фиксировать в логах вместе с версией образа и revision модели.
- Checkpoint занял 30.98 GiB, модель — 31.71 GiB. KV cache занял 5.95 GiB и
  вмещал 14 668 токенов. Оценка vLLM `1.79×` относилась только к запросам длиной
  8192 токена; она не является пределом параллельности для коротких запросов.
- 60 ГБ Pod volume после загрузки занимал около 32 ГБ, поэтому 50 ГБ может
  оказаться достаточно. Для следующего опыта размер выбирается с запасом после
  проверки состава cache; агрессивно уменьшать том ради небольшой экономии не
  нужно.

## Проведение измерений

- Сначала искать публичные замеры для точной модели, квантизации, GPU и runtime.
  Замер API-провайдера на неизвестном железе не заменяет сопоставимый baseline.
  Если опубликованных данных недостаточно, снять свой исходный результат и
  проверять конкретную гипотезу, а не перебирать настройки вслепую.
- Использовать один набор production prompts и одинаковые sampling settings.
  Первый прогон каждого нового текста в vLLM исключать как warm-up.
- [`load_benchmark.py`](load_benchmark.py) измеряет TTFT, полную задержку,
  tokens/s, throughput, ошибки и корректность формата по стадиям. Он не делает
  retry, сохраняет каждый завершённый запрос в `.progress.jsonl` и атомарно
  фиксирует завершённые уровни.
- При первой ошибке или невалидном ответе не продолжать очередь и не повторять
  запуск без разрешения. В этом опыте завершение процесса совпало с проверкой
  состояния, и пустой буфер был ошибочно принят за потерянный запуск; новый
  запуск успел начаться до обнаружения готового артефакта. Поэтому полный stdout
  надо писать в `/tmp`, вывод делать unbuffered, проверять exit code, процесс и
  артефакт вместе.
- Системный API логов Runpod ограничен по объёму и может зависнуть на длинном
  чтении. В этом опыте `source=both` обрывал соединение, а отдельный
  `source=system` с `maxWaitMs=1000` работал. Отсутствие новых строк в коротком
  окне не означает зависание: проверить также последние сохранённые события.
  Локальный benchmark сохраняет полный собственный буфер отдельно.

## Ключи и завершение

- Секрет передаётся через Runpod environment или stdin временного процесса. Не
  помещать его в Docker args, командную строку, артефакты и вывод. В документах
  сохраняются только host, model id и тип аутентификации. Ответы MCP на
  `get/list/create/stop` могут содержать весь `env`: выводить только заранее
  выбранные безопасные поля, не печатать ответ целиком.
- Перед остановкой скопировать сырые результаты и sidecar metadata, проверить
  число строк и ошибки. Сначала остановить compute, затем по принятому решению
  удалить Pod или оставить оплачиваемый том.
- Для одноразового опыта после удаления независимо проверить пустые списки Pods
  и network volumes. Состояние на 2026-09-12: оба списка пусты.
