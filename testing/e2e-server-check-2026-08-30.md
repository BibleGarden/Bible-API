эталон 0.7.0 прогнан на текущем коде с релизной моделью rewrite `gemini-3.7-flash`

(11960 векторов) не тронут, коммитов нет.

## 3. Benchmark против порогов

### Можно ли было прогнать на релизной модели без живых вызовов — да

Разбор кэшей `evaluation/bench_data/`:

* `pipeline_cache.json` — три раздела: `rewrites` (274 ключа),
  `query_embeddings` (1693), `reranks` (457).
* Ключ rewrite — `{модель}|p{REWRITE_PROMPT_VERSION}|n{variants}|{scenario_id}`.

  пулом **до** стадии rewrite, живого вызова не требует вовсе.
* Ключ эмбеддинга — хэш текста запроса; ключ rerank включает хэш списка
  кандидатов. Раз варианты берутся из кэша побайтово, оба следующих слоя тоже

диска. Он и был выполнен — на **текущем коде**, а не переписан из README.

## 5. Приватность

### 5.1 Логи контейнера

В темы запросов был заранее вставлен уникальный маркер `QQZX7714`
(сценарий `long_topic`).

```bash
docker logs bible-api 2>&1 | grep -c "QQZX7714"        # -> 0
docker logs bible-api 2>&1 | grep -iE "операц|Умерла мама|дочери"  # -> пусто
```

Текста молитвенных тем, реплик пользователя и выбранных отрывков в логах **нет**.
Логи содержат только access-строки uvicorn вида
`INFO: 172.22.0.1:47556 - "POST /api/ai/scripture HTTP/1.1" 200 OK`.

Замечание (не дефект): access-лог uvicorn пишет сырой адрес клиента для
`/api/ai/*`. Это stdout контейнера, а не хранимая статистика; ADR формулирует
запрет для темы/реплик/отрывка, IP в этот список не входит. Псевдонимизация
`PRIVATE_PATHS` относится к `api_requests`, и там она работает (ниже).

## 7. Дефекты

### D-1. На проде стадия rewrite работает на модели, провалившей пороги — **major**

**Что.** В прод-`.env` (`/root/cep/bible-api/.env` на `bible.garden`):
`AI_SCRIPTURE_REWRITE_MODEL=gemini-3.5-flash-lite`, а
`AI_SCRIPTURE_REWRITE_API_KEY` не задана (длина 0), то есть rewrite идёт по
общему `GEMINI_API_KEY`.

**Почему это дефект.** Rewrite — доминирующий рычаг качества (ADR 0004), и
значение модели «прибито бенчмарком». На `gemini-3.5-flash-lite` эталон
проваливает `retrieval_top_k`: recall@10 **0.554** при пороге ≥ 0.60 и MRR 0.529
при пороге ≥ 0.60 (пакет 2026-08-29, `evaluation/README.md`). Прод сейчас отдаёт
пользователям подбор того качества, которое приёмку не проходит. Локально то же
самое, но локально это осознанное решение Марии ради экономии на период
разработки; для прода такого решения в документации нет — `Deploy/env-checklist.md`
и CLAUDE.md называют релизным значением `gemini-3.7-flash`.

**Воспроизведение.**
```bash
ssh bible.garden 'grep "^AI_SCRIPTURE_REWRITE_MODEL=" /root/cep/bible-api/.env'
# AI_SCRIPTURE_REWRITE_MODEL=gemini-3.5-flash-lite
ssh bible.garden 'grep -c "^AI_SCRIPTURE_REWRITE_API_KEY=$" /root/cep/bible-api/.env'
# 1  -> переменная пуста
```

**Что нужно.** Решение Марии: либо ставим на проде `gemini-3.7-flash` вместе с
платным `AI_SCRIPTURE_REWRITE_API_KEY` (free-tier 3.7-flash — 20 запросов в
сутки, для прода неприменим), либо явно фиксируем в `Deploy/env-checklist.md`,
что прод сознательно живёт на lite до оплаты ключа, и приёмка качества
переносится. Ничего на проде я не менял.

### D-2. Полное время ответа не ограничено бюджетом `AI_SCRIPTURE_TIMEOUT_SECONDS` — **minor**

**Что.** Медиана подбора — 3.5 с (прод 4.1-4.6 с), но хвост длинный:
`long_topic` — 12.9 с, контрольный запрос при 429 от провайдера — **16.3 с** при
объявленном бюджете **15 с**. Ответ корректный (200,
`retrieval_fallback` / `rerank_failed`, не 5xx), но клиент ждал дольше бюджета,
на который рассчитан таймаут мобильного приложения.

**Воспроизведение.** Выбрать дневную free-квоту lite-модели (несколько десятков
подборов), затем один подбор:
```
HTTP=200 TIME=16.302237  source=retrieval_fallback fallback=rerank_failed
# в логе: passage rerank failed: rerank request failed after retries
```

**Оговорка.** Условия локального стенда искусственные: free-tier lite отдаёт 429,
retry-лестница провайдера съедает бюджет. На проде с оплаченным ключом хвост
должен быть короче. Тем не менее стоит проверить, что `Deadline` действительно
режет ответ по 15 с, а не только решает, какую стадию пропустить, и согласовать
таймаут мобильного клиента с реальным хвостом (12-16 с), а не с номинальными 15 с.

### D-3. Повторный безопасный пул отдаёт тот же отрывок — **info, не дефект**

При `ai_unavailable` два подряд запроса без `exclude_canonical_ids` вернули один и
тот же `v3:19.023.001-006`. Это ожидаемое поведение (ротация пула опирается на
переданные исключения), фиксирую, чтобы мобильная половина не приняла за баг:
клиент обязан складывать показанные `canonical_id` в `exclude_canonical_ids`.

### D-4. `_final_top1_report` печатает строгий раздел порогов для coverage-прогонов — **cosmetic**

Известно и задокументировано (`evaluation/README.md`), пороги
`final_top1_coverage_restricted` считаются вручную. В логе coverage-прогона
`sensitive relevant 0.857 >= 1.0 -> FAIL` — это ложная тревога инструмента, а не
провал. Стоит когда-нибудь научить `_final_top1_report` выбирать раздел по
наличию `--coverage-translation`, чтобы никто не прочитал лог буквально.
